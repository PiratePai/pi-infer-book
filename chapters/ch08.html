第 8 章 · 执行优化：融合、图捕获与数据搬运 ​

前两章优化的是算什么（跳块、少搬中间量）。本章优化的是怎么执行：同一段计算，为什么提交给设备的方式不同，时间就差很多？第 3 章的 profiler 已经给过预告——view/as_strided 这类"元数据算子"调用了上千次。本章的问题是：一次前向被切成的几千个小步骤，每一步的"提交"本身要花多少钱？这笔钱怎么省？

三个治理对象对应三节：小算子的提交开销（8.1/8.2 融合）、整段执行图的重复提交（8.3 CUDA Graph）、搬运与同步的交错（8.4）。实验在 experiments/exp_ch8_exec/。本机无 NVIDIA GPU：CPU 侧机制与相对量级实测签收，设备端行为（真实图捕获、私有内存池、H2D）一律标"未测"（5.3），代码按官方约束就绪交付。

8.1 一段执行的四层时间：提交、启动、计算、等待 ​

把"模型跑一步"拆开看，时间花在四个不同的地方：

层发生在哪本机可测？
CPU 提交Python → ATen 分发、参数检查、shape 推导✓
kernel 启动驱动把算子放进设备队列CUDA 上显著，CPU 并入提交
设备计算算子真正执行CPU 上与提交交织
同步等待等 GPU/等传输/等另一个线程✓（线程间）

实测每个小算子的提交开销（X2）：对 [64] 张量做 1000 次逐元素加法 vs 一次加上 1000.0 的塌缩单算子，差值除以 1000——≈2.1 µs/算子（本机 CPU，双方预热+成对交错 7 轮）。单看微不足道；但第 3 章 E4 里一次 decode 循环有近千次算子调用，一次 prefill 更多——提交开销 ≈ 算子数 × 2.1 µs，这就是"小算子多到一定程度，Python 层调度盖过计算本身"的算术。

改动由 trace 指向（验收要求）：X1 用 torch.profiler 采集一段 50 次重复的小算子链（mm→silu→mul→mm），top-8 表存档（x1_profiler_top8.txt）——元数据/分发类算子占 self 时间 3–4%，数值计算本体外还有一整层可削的"账面工作"。这与第 3 章"先看结构再下结论"是同一条纪律：先采 trace，再选优化对象，不凭感觉融合。

8.2 融合：少一次中间读写，少一次提交 ​

融合的原理第 6 章已经用过（FlashAttention 把三个算子融进一个内核）。这里用最小的两算子例子把收益与代价都摆出来——SwiGLU 的中间乘法（第 2 章 2.3）：

python
h = silu(gate(x))     # 物化中间量 [T, d_ff]
h = h * up(x)         # 再物化一个 [T, d_ff]
out = down(h)

2
3

两个连续算子 silu 与 mul 各自提交、各自把 [T,d_ff] 写一遍再读回来。融合的理想界：一个内核内完成，中间量留在寄存器——0 次物化。本书用可测的代理量化两头之间的距离（X3，T=32、d_ff=176、fp32）：

变体中间物化时间（同机相对）
out-of-place（两次物化）2 × [32,176] fp32 = 45,056 B0.091 ms
in-place（h.mul_(up(x))，一次物化）22,528 B0.080 ms
融合理想界0 B未测（无编译器/设备）

三个诚实的读数：字节账如预期减半（2→1 个中间张量）；成对交错计时下 in-place 快约 12%——方向符合预期，但时间收益远小于字节减半的比例：CPU 分配器缓存下"少物化一个张量"近乎免费，省下的主要是分配与一遍读写；真融合内核本机不可得——torch.compile 报"找不到 C++ 编译器（cl）"，如实记为缺项（环境缺项与探测代码错误已区分记录）。这组数字的教学价值恰恰在量级感：融合改善的是"中间量往返 + 提交次数"，前者在 HBM 受限的设备上是硬收益（第 6 章 F2 已证内存口径），后者是 8.1 的 2.1 µs × 削掉的算子数——CPU 小尺度上两者都只给出温和的相对收益。融合的可用条件也随之清楚：数值等价可验证（本例 allclose 逐位成立）、shape 固定或可特化、内核确实存在（编译器或手写）——三者缺一，融合只是愿望。

8.3 CUDA Graph：把"整段提交"变成"一次重放" ​

即使算子已经很好，decode 每步仍要重新提交几百个算子。CUDA Graph 的思路：第一次老老实实执行并把整段算子调用录制成图，之后每次只提交"重放"这一个动作——官方文档的约束清单（references S26）就是它的代价表：

  1. 捕获须在非默认流，且捕获前在 side stream 上预热（线程池、惰性初始化都留在预热里）；
  2. 动态 shape 与 CPU 侧控制流禁止——每次重放"读写同一（虚拟）内存地址"，shape 变了图就错了；
  3. 静态输入/输出缓冲：新数据 static_input.copy_(x) 喂进去、从捕获时的输出缓冲读出来——这部分额外内存是图的重放语义决定的；
  4. 捕获期间禁止 .item() 等 CPU-GPU 同步；API 尚属 beta。

本书交付的 cuda_graph_ready.py 把这套工作流写成设备分支守卫的代码：CudaGraphRunner 在 CUDA 可用时走"side-stream 预热 → torch.cuda.graph 捕获 → copy_ 喂入 → replay()"，输入签名（shape/dtype/device）变化时显式重捕获而不是静默出错；CPU 上捕获路径显式拒绝（报错信息说明原因），调用走可观测的 eager 回退计数。本机自检（X4）：graphed=False（未捕获，如实），回退计数与静态缓冲记账（本例 512 B）工作正常，动态 shape 的拒绝路径有断言。

图与编译分别计量（验收条款）：CUDA Graph 治理的是提交/启动次数（同一段算子，一次提交），编译/融合治理的是算子本身的数量与形态——两者独立起效、收益可乘也可互斥（编译产物若含动态分支就不可捕获）。设备端两者的真实收益本机未测；CPU 侧能测的是它们共同治理的对象——8.1 的每算子 2.1 µs，乘以一步 decode 的算子数就是图重放在 CUDA 上的期望收益量级（真实数字须设备实测）。

8.4 数据搬运与同步：让"等"和"算"重叠 ​

主机—设备传输是第四类成本。没有 GPU 时它的机制仍可以用 CPU 讲清楚，因为本质相同：搬运与计算是两份资源，同步点决定它们能不能重叠。X5 的双线程流水线（生产者造数据、消费者算，24 批）做了两组对照：

生产者串行交接预取队列（深度 2）相对
纯计算（小算子）0.0502 s0.0442 s1.14×
阻塞 I/O（写读磁盘）0.1390 s0.1047 s1.33×

两个变体一正一负，正好把机制讲透：重叠的前提是有一方真正在"等"。纯计算生产者与消费者都抢同一个 intra-op 线程池——串行时每个算子已经多核并行了，重叠空间所剩无几（1.14×，远低于理想 2×）；阻塞 I/O 生产者（磁盘写读、释放 GIL——DMA 传输的 CPU 类比）在串行时让计算侧干等，预取队列把"等 I/O"与"算上一批"叠起来，1.33×。映射到 GPU 场景：to(device, non_blocking=True) 配 pinned memory 让 H2D 由 DMA 引擎搬、计算单元同时算上一批——同一纪律，未测设备（按官方文档登记口径）。减少无意义同步的另一面：每个 cuda.synchronize()/.item() 都是把流水线打回串行的接缝——第 3 章计时纪律要求"只在读表前同步"，在生成循环里就是"别每步都取数回 CPU"。

练习与答案 ​

练习 1：一步 decode 有 800 个算子调用，其中 200 个是 view/reshape 类元数据操作。按本章实测每算子 2.5 µs，仅提交开销是多少？若图重放把整步变成一次提交，省多少？答：800×2.1 µs=1.7 ms/步；TPOT 若为 20 ms，提交占 10%。图重放把这 2.0 ms 压到一次提交（µs 级），省 ≈10%——但注意重放不减少设备端计算，若瓶颈在计算（大 batch），收益按比例缩水：提交开销占比多大，图收益才多大。

练习 2：为什么 CUDA Graph 要求静态 shape 与静态内存，而 PyTorch eager 不要求？答：eager 每次调用都重新分配、重新传参——慢但任意 shape 都行；图把"哪段内存被哪个算子读写"固化在录制里，重放只是让设备按录制的地址序列再跑一遍——地址变了内容就错。所以引擎用图要配合 padding 到固定长度或按 bucket 捕获多张图，这正是 X4 显式重捕获分支存在的意义。

练习 3：X3 里 in-place 只快了 12%，而字节省了一半。有人说"融合的收益被夸大了"。对吗？答：半对——收益必须按资源维度分开报：字节维度 in-place 实打实省 50%（45,056→22,528 B），时间维度只省 12%（分配器缓存下物化近乎免费，省的是一遍读写）；融合（把中间量留在寄存器）在 CPU 小尺度上与 in-place 同一量级，其"字节省 100%"的完整收益要 HBM 受限的设备才兑现（第 6 章 F2 内存口径）。"优化"从来是"在哪个资源维度上省多少"，不是单一"快不快"。

练习 4：把 X5 的消费者改成每消费一批就 queue.task_done() 并等待生产者的下一批（严格锁步），预期流水收益如何变化？答：趋近 1.0×（串行交接的等价物）——锁步等于在每个边界插入同步点，"等"与"算"不再重叠。预取队列的收益来自深度允许的错峰：消费者永远有活干，生产者的阻塞被藏进消费时间。深度也不是越大越好：内存占用与首批延迟随深度增长。

练习 5：一条生产建议说"把循环里所有 .item() 都删掉"。给出一个不能删的反例。答：停止条件——next_id == eos_id 的判断必须把 argmax 结果拿回 CPU（.item()），否则循环无法终止。正确的治理是减少同步点的个数而不是消灭：每步一次（判断停止）是必要的，每步多次（日志、指标、调试打印）才是被治理的对象；投机解码（第 7 章）一次前向换多个 token，恰好也把"每 token 一次的 CPU 交互"摊薄了。

小结：算了什么、慢在哪里、怎样验证 ​

  • 一段执行的时间=提交+启动+计算+等待四层；小算子提交开销实测 ≈2.5 µs/个，机制上由融合（减少算子数）与 CUDA Graph（减少提交次数）分别治理——两者独立计量、可叠加；
  • 融合的收益维度是中间物化字节与提交次数，可用条件是数值等价+shape 固定+内核存在；本机代理实验显示 CPU 时间维度无收益（如实报告），字节维度收益真实；
  • CUDA Graph 的约束（静态 shape/内存、side-stream 预热、静态缓冲喂入）就是它的代价表；代码就绪交付、设备行为未测；图治提交、编译治算子形态——分别计量不混谈；
  • 搬运与同步：重叠的前提是一方真正阻塞（I/O/DMA），纯计算双线程只是竞争；同步点是流水的接缝，能少则少、必要的（停止判断）保留。
