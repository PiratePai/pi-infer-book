第 6 章 · FlashAttention：精确计算中的 IO 优化 ​

第 5 章的两条路（低精度、稀疏）都改变了语义：数值或连接模式不再与稠密 fp32 相同，所以要配质量预算。本章走第三条路：一个比特都不改、一个连接都不删，只减少中间数据的搬运。结果与标准注意力在浮点误差内逐位一致——"精确计算中的 IO 优化"。

问题从 6.1 的一笔账开始：标准注意力实现要把多大的中间矩阵写出去再读回来？答案是 O(T2)——上下文越长越荒谬。解法（online softmax）让中间量降为 O(T)。配套实现 pi_infer/flash.py，实验 experiments/exp_ch6_flash/。

6.1 标准注意力的 HBM 往返 ​

按第 2 章的手算流程，标准实现分三步，Q,K,V∈RT×dh：

S=QK⊤dh ∈RT×T,P=softmax(S) ∈RT×T,O=PV ∈RT×dh

三步在朴素实现里是三个独立算子：S 要完整写到内存，softmax 再把它整个读回来写出 P，第三次读回 P 算 O。以 fp32、单头 T=2048 计（实验 F2 的实测口径）：S 与 P 各 ≈16.8 MB，一写一读两轮，中间临时量合计 60+ MB——而 Q,K,V,O 四个"真数据"只有 4×2048×128×4B≈4.2 MB。中间量是有效数据的十几倍，全部要走最慢的那层内存（GPU 上即 HBM：寄存器/共享内存快一至两个数量级，但容量装不下 T2）。

分块（tiling）的障碍在 softmax：它是整行的归一化——分块算了半行的 P，没有整行的分母就除不了。硬要先除局部和，合并时数值会严重失真。绕开这个障碍就是 6.2 的 online softmax。

6.2 从稳定 softmax 到 online softmax：逐块合并公式 ​

第 2 章的稳定 softmax 是"减去整行最大值"。online softmax 把"整行统计量"变成随块更新的三个 running 量：当前见过的最大值 m、指数和 ℓ、未归一化输出 O~。处理新块（块内统计量带下标 b：mb=max(块内行), ℓb=∑es−mb, O~b）时，合并公式为：

mnew=max(m, mb),α=em−mnew,β=emb−mnewℓnew=ℓα+ℓbβ,O~new=O~α+O~bβ (O~b=∑jesj−mbvj)

全部输入处理完后 O=O~/ℓ。手算一次合并（闭合验算版；test_flash.py 的单步用例同源）。设某行已有旧块统计（在旧基准 m=2 下）：m=2, ℓ=2, O~=8——它对应旧块分数 {2,2}、v={4,4}（e0+e0=2，4e0+4e0=8）。新块分数 {3,1}、v={1,5}：

text
m_new = max(2,3) = 3
α = e^{2-3} ≈ 0.3679          β = e^{3-3} = 1
ℓ_new = 2×0.3679 + (e^{0}+e^{-2})×1 ≈ 0.7358 + 1.1353 = 1.8711
Õ_new = 8×0.3679 + (e^{0}×1 + e^{-2}×5)×1 ≈ 2.9430 + 1.6767 = 4.6197
该行最终 O = 4.6197 / 1.8711 ≈ 2.469

手算时最容易错的一点：旧块的 (ℓ,O~) 必须与旧基准 m 同基准给定（练习 3 进一步问"漏乘 α 会怎样"）。合并公式的三个不变量值得记住：处理顺序无关、任意分块大小结果相同、全零块不改变结果——F1 的 block=64..1 全部对齐就是实证。

6.3 小规模分块实现：对齐、内存与时间 ​

pi_infer/flash.py 提供同一 GQA 接口的两个实现：flash_attention_reference（显式物化 S,P）与 online_softmax_attention（分块 + running 量），并带 FlashStats——在实现内部登记"同时存活的中间张量峰值字节"（口径：显式分配的 scores/概率/running/临时量，不含输入输出与算子内部工作区）。

F1 数值对齐（GQA、T=128）：block=64/16/4/1 与参考 max|Δ|≤4.8e-07 全部 allclose——精确语义保持，误差只是浮点求和顺序不同。

区分三件事，验收时不得混谈：精确语义（逐位对齐，F1）、浮点误差（求和顺序差异，1e-07 量级）、复杂度（计算不变 O(T2dh)，访存 O(T2)→O(T)）。

6.4 使用成熟注意力内核：检查清单 ​

生产中不要手写内核，用 scaled_dot_product_attention（SDPA）或引擎自带的 FlashAttention 路径。接入时的检查清单（每项都可能让"看似一样"的实现悄悄出错）：

  1. dtype：fp16/bf16 内核对累加精度的处理与 fp32 参考不同——对照时用同 dtype 参考或放宽容差并记录；
  2. shape 与 head 维：[B,H,T,D] 布局；GQA 需先 repeat 或用原生 enable_gqa 类参数（版本相关）；
  3. mask 语义：is_causal=True 是"从 0 起的 j≤i"；右对齐（增量解码的尾块）要显式 mask——语义错了 F1 式对齐会立刻暴露，前提是你做了对齐；
  4. 缓存布局：第 4 章分页缓存的 KV 不是连续张量，内核要支持 block table（生产 FlashAttention 的 paged 变体）或先 gather（回到拷贝成本）；
  5. 后端回退：SDPA 在不满足条件时静默回退到数学实现——性能假设可能不成立，用文档列出的查询接口核对实际后端。

本书实验环境完成的是"清单代码就绪 + CPU 分支验证"：F4 实测 SDPA(CPU) 与我们的参考 allclose（1e-05）；CUDA/Flash 后端的真机行为未测（5.3）。原理实现与生产内核各自验证什么：前者验证公式与内存口径（F1/F2），后者验证工程条件下的正确性与性能——第 15 章部署时再补后者的实测。

Triton 内核编写是好的额外实践（在 6.2 公式与 6.4 清单之间搭桥），但不是本书正文的依赖。

练习与答案 ​

练习 1：T=4096、fp32、单头，标准实现要物化多大的中间量？比 Q,K,V,O 总和大几倍？答：S,P 各 40962×4B=64 MiB，合计 128 MiB；Q,K,V,O 合计 4×4096×dh×4 B，dh=128 时 ≈8 MiB——16 倍。这就是 F2 曲线在真实规模下的样子（长上下文模型 T 以万计时中间量直接到 GB 级）。

练习 2：把 6.2 手算例的旧块取分数 {2,2}、v={4,4}（m=2、ℓ=2、Õ=8），新块不变（分数 {3,1}、v={1,5}）。手工合并并验算。答：mnew=3,α=e−1≈0.3679,β=1；ℓ=2(0.3679)+(1+e−2)=1.8711；O~=8(0.3679)+(1+5e−2)=4.6197；O=4.6197/1.8711≈2.469。验算（全行 softmax）：分数 {2,2,3,1}→幂（减最大值 3）{.368,.368,1,.135}，和 1.871 ✓；O=(.368×4+.368×4+1×1+.135×5)/1.8711=4.6197/1.8711≈2.469 ✓ 闭合（与 6.2 手算例同一行，两处互证）。

练习 3：为什么 online softmax 的合并必须乘 α=em−mnew？丢掉它会怎样？答：O~ 与 ℓ 是在旧基准 m 下的指数和；新块把基准改到 mnew 后，旧贡献要整体缩放到新基准（乘 \em−mnew）才能与新块贡献相加。丢掉 α：两块基准不同却直接相加——软最大值的分母错误，结果不再是 softmax（对齐测试会立刻失败；这也是实现时最容易漏的一行）。

练习 4：F3 里 online 在 CPU 上更慢，为什么 FlashAttention 在 GPU 上仍是标配？答：CPU 上瓶颈是 Python 循环与小块调度开销，而朴素实现的"内存往返"在 CPU 缓存足够大时惩罚有限；GPU 上 HBM 带宽远低于算力（第 3 章脊点），T2 中间量的往返成为真瓶颈，融合内核把块留在寄存器/共享内存里，收益盖过分块开销。同一算法在不同带宽/算力比的设备上结论不同——第 3 章 Roofline 的直接应用。

练习 5：SDPA 接入分页 KV 缓存（第 4 章），直接把 PagedRequestCache.get() 的 gather 结果喂进去有什么代价？何时可以接受？答：get() 的跨块 gather 本身就是一次 O(T⋅dh) 拷贝——把"内核省掉的中间量"又以拷贝形式付了一部分回来。可以接受的场景：调试与正确性验证、或 gather 成本相对注意力 O(T2) 仍然很小的短序列；长序列高并发生产路径要用支持 block table 的 paged 内核（6.4 清单第 4 条）。

小结：算了什么、慢在哪里、怎样验证 ​

  • 标准注意力的中间量 S,P 各 O(T2)，长上下文时比有效数据大一个数量级——慢在往返不在计算；
  • online softmax 用 running (m,ℓ,O~) 与合并公式把中间存储降到 O(T)，精确语义不变（任意块大小逐位对齐）；手算合并是掌握它的最短路径；
  • 实测三个层次：数值（≤4.8e-07）、峰值内存（T=2048 时 0.1%）、时间（CPU 上更慢——IO 优化的收益在带宽受限设备兑现）；
  • 验证改动：参考实现对齐 + 合并公式单步闭环 + 峰值计量口径写明；生产内核按 6.4 清单逐项核对。
