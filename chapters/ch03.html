第 3 章 · 算账、计时与性能定位 ​

第 2 章我们让前向"跑对了"。本章的问题是：它跑得多快、慢在哪、怎么量才不作假？ 顺序是先会算（FLOPs 与字节数的账）、再会量（计时的坑）、最后会看（profiler 与时间线）。本章建立起的全书测量纪律——手算在测量之前、口径先于数字——是后面每一章实验的公共地基。

本机无 NVIDIA GPU，本章全部实测在 CPU 上做相对对照；设备侧绝对性能与 CUDA trace 标"未测"（5.3 降级口径），方法与脚本对 CUDA 路径同样适用（内置 sync_device 分支）。

3.1 先把账算出来：FLOPs 与字节数 ​

一次前向的成本只有两个来源：计算（乘加）与搬运（读写字节）。先手算，再测量——顺序不能反，否则测出的数字无物可对。

权重账（tiny 配置，fp32）：

项参数量字节
embeddingV×d=256×64 = 16,38464 KB
每层 proj（q/k/v/o 4 个）4d2 = 16,38464 KB
每层 FFN（gate/up/down 3 个）3d⋅dff = 33,792132 KB
× 2 层 + norms + lm_head合计 ≈ 0.10M≈ 0.40 MB

FLOPs 账。线性层 y=Wx（x∈Rdin）每输出一个元素是 din 次乘加；一个 token 过全部权重 ≈2×参数量 FLOPs。所以：

  • prefill T 个 token 一次前向 ≈2Params⋅T（所有 token 的矩阵乘可以堆成大 GEMM，算力吃得满）；
  • decode 每一个 token 也要过全部权重（2Params），但 batch=1 时是 GEMV——矩阵搬运一样多、每个字节只喂一行乘法，算术强度暴跌，这就是 decode 天然偏向带宽受限的原因（3.2 展开）。

KV 账（每 token、fp32、GQA）：

KVBytes/token=2⏟K,V×nlayer×hkv×dh×4B=2×2×2×16×4=512 B

对照 MHA（hkv=hq=4）：1024 B/token——GQA 让缓存账直接减半，这就是第 2 章"K/V 头数更少"那行的代价收益表。上下文越长，这项账越主导：T=128 时 tiny 的 KV（64 KB）已与权重同量级；真实模型（28 层、128 维、40960 上下文）这一项是 GB 级，第 4 章整章都在管它。

三笔账合起来回答"这次前向该花多少"：FLOPs 给计算下限，字节数给搬运下限，剩下的差距就是实现效率的空间。

3.2 算术强度与 Roofline：先判断"该"慢在哪 ​

把两本账相除得到算术强度（FLOP/Byte）。Roofline 模型给出上界：

Timemin=max(FLOPsπpeak, Bytesβpeak),脊点=πpeakβpeak
  • 强度低于脊点 → 带宽受限：时间下界由搬运决定，优化方向是少搬（缓存、融合、低精度字节）；
  • 高于脊点 → 计算受限：优化方向是少算（跳过、稀疏）或提高算力利用率。

关键是不把结论写死：prefill 与 decode 的强度天差地别（大 GEMM vs GEMV），batch 变大时 decode 又会重新爬回计算受限——"decode=带宽受限"只在 batch 小时成立。直觉版：batch=n 时同一份权重字节喂 n 行乘法，强度近似 ×n。

实验 run_timing_experiment.py 的 E3 用标称参数走一遍判定流程（强度=x vs 脊点=y），并把"标称、未实测"写进结论——真实 βpeak 要用 3.4 的规范计时跑出来。

3.3 指标：TTFT、TPOT、ITL、tok/s——分母和样本单位先说清 ​

指标定义分母/样本单位
TTFT首 token 延迟（含排队+prefill）每请求一个样本
TPOT生成阶段平均每 token 时间每请求一个样本（(总时间−TTFT)/(输出数−1)）
ITL相邻 token 间隔每 token 一个样本，分布含长尾
tok/s吞吐必须注明分母：输入/输出/合计
req/s请求吞吐每请求一个样本

两个约定，全书沿用：平均值按请求、ITL 按 token 分开统计——"平均 TPOT 很好看但 p99 ITL 长尾爆炸"是服务最常见的病灶；tok/s 一律标注分母（输出 token 计还是输入+输出合计），第 9 章起直接引用。SLO 的最小定义也在此固定：对哪些指标设线（如 TTFT p95 < 300ms）、分位数样本单位是请求还是 token——第 9 章的容量曲线照此口径画。

第 1 章的实测在这里正式入账：流式事件 first_token 162ms（= 单请求 TTFT，无排队成分）、后续均值 ≈55ms（≈TPOT；ITL 的原始样本在事件流里，逐 token 可取）。

3.4 计时的坑：不同步就计时，会看到假加速 ​

设备执行是异步的：Python 发出 kernel 启动就返回，真正的计算在设备队列里排队。计时结束前不同步，表上的时间只是"提交时间"——尤其配上"优化后 kernel 启动更快"，会得出完全反向的结论。

规范做法四件套（experiments/exp_ch3_timing_bottleneck/run_timing_experiment.py）：

  1. 同步：计时窗口内 torch.cuda.synchronize()（脚本 sync_device()；CPU 上为空操作但调用点保留）；
  2. 预热：丢弃前几次（线程池、首 kernel、缓存、编译都在里面），至读数稳定；
  3. 交错重复：baseline 与 candidate 交替跑，而不是各跑一串——把机器状态漂移摊到两边；报均值±std；
  4. 窗口完整：从输入构造后到全部输出（含最后一步）结束。

实验 E1：先错一次，再对一次。 同一段工作（prompt=32、生成 16 token），实测：

正确口径            16.41 ± 2.59 ms（预热3 × 交错重复5）

（实测于本机 CPU，raw.json 可复跑核对。）无预热稳定高估 30–50%。缺尾在本例只低估 1%——tiny 模型在 CPU 上 prefill 占了大头、单步 decode 不足 1ms；真实部署里 decode 是大头，同样的缺尾会漏掉 10% 量级。偏差大小取决于漏掉的部分占多大比重，但方向永远是错的。CUDA 上还有第三种：不同步计时叠加异步执行，几乎总是"假加速"，脚本保留该分支，本机无卡未测。

此外记住两个状态词：冷启动/编译/冷缓存/热缓存/稳态要分别标注；显存有 allocated（张量实际占用）与 reserved（分配器预留）两个数，报哪个要写明——CPU 上对应进程 RSS，本机未测。

3.5 把时间线对上：客户端、日志、设备 ​

一个延迟数字拆开是四段：排队 → CPU 提交 → 设备执行 → 等待。定位瓶颈就是确认时间落在哪段：客户端时间戳给端到端；服务日志给排队与每步调度；profiler 给算子级。三层时间线对得上，结论才立得住——第 1 章练习 3 的"日志有 done 但客户端没收到"就是三层对齐定位到传输层的实例。本机 CPU 实验里"CPU 提交"与"设备执行"合并为一个进程，第 15 章部署实验再把三层拆开对表。

3.6 统一测量入口：扫描只动一个因素 ​

E2 的扫描纪律固化为可复用入口（pi_infer/bench.py，第 5/6 章直接调用）：每次只动一个研究因素（输入长度 / 生成长度 / batch 之一），其余固定；每点预热 + 交错重复，报均值±std 与原始样本；sync_device 调用点保留。单因素纪律的目的不是好看，而是让"X 变大导致 Y 变慢"这类结论可归因——多因素同变时，斜率无法解释。

练习与答案 ​

练习 1：tiny 模型 batch=1 decode 单 token 的算术强度是多少（只算权重搬运）？答案：FLOPs ≈2×0.10M=0.2M，字节 ≈0.40 MB，强度 ≈0.5 FLOP/B——远低于任何设备的脊点（CPU 标称脊点 5 FLOP/B、GPU 通常 >10），所以小 batch decode 必然带宽受限，优化方向是"少搬字节"而不是"算得更快"。

练习 2：某服务 100 个请求的 ITL 样本（每 token 一个）里，99 个 ≈20ms、1 个 500ms；另 100 个请求的 TTFT 均值 100ms。平均 ITL 与最差 ITL 差多少倍？这说明什么？答案：均值 ≈24.8ms，最差 500ms，相差 20 倍——均值掩盖长尾；按请求平均的指标（TPOT）与按 token 的分布（ITL）必须分开统计，SLO 若只绑均值就会放过这 1% 的卡顿（3.3 两条约定的由来）。

练习 3：三种计时：A）首次调用即计时；B）预热后计时，但循环结束立刻读表（CUDA）；C）预热后计时，读表前 synchronize。哪些可信？答案：C 可信。A 含初始化开销（E1 实测 +46%）；B 在 CUDA 异步执行下读到的是提交时间——排队中的 kernel 尚未完成，"优化"若只是让提交更快会显示假加速；CPU 上 B 因进程内串行恰好近似 C，但方法不可迁移。

练习 4：输入长度 T 多大时，tiny 的 KV 字节超过权重字节（fp32）？答案（按 3.1 表的合计口径 ≈0.10M 参数、0.40 MB）：KV 512 B/token → T≈800（逐项精确清点参数时 T 略小、量级不变；超出 tiny 的 max_seq_len=128，但真实模型 40960 上下文下 KV 远超权重——同一公式换个量级，这就是第 4 章"KV 是主战场"的算术根据）。

练习 5：把 decode 的 batch 提到 32，算术强度如何变化？会翻过脊点吗？答案：权重字节不变而 FLOPs ×32，强度 ≈0.5×32=16 FLOP/B（忽略 KV 增量）——超过标称 CPU 脊点（5），decode 从带宽受限爬向计算受限。这解释了生产引擎为什么用大 batch 换吞吐（第 9 章），也说明"decode=带宽受限"是有条件的结论。

小结：算了什么、慢在哪、怎样验证 ​

  • FLOPs≈2×参数量/token、KV 字节/token、算术强度——三笔账在测量之前先手算，prefill 与 decode 分开算；
  • 计时四件套：同步、预热、交错重复、窗口完整；先错一次再对一次，数字才有"防伪标签"；
  • 指标口径：请求均值与逐 token 样本分开、tok/s 标分母——第 9 章容量曲线的地基；
  • profiler 只回答"时间花在哪类算子"，"该不该"要拿 3.1 的账对表。

下一章把最大的那笔搬运账——KV——变成可管理的对象：分块、分配、复用。
