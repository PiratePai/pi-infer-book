第 13 章 · VLM：从图像输入到文本生成 ​

前十二章的请求都只有文字。把一张图放进请求，语言模型并不"看图"——图被换算成一串 token，拼进 prompt，走的是同一条 prefill→decode 流水线。本章的问题是：一张图到底变成多少个 token？这些 token 的成本落在哪一段？该先改输入、调度还是执行？

锚定模型 Qwen3-VL-4B-Instruct（外挂式视觉塔，S30/S31；6.4 的安排：外挂式便于分阶段计时，Qwen3.5 原生多模态仅作对照案例、不展开）。实验 experiments/exp_ch13_vlm/。本机无 VLM 运行环境（5.3）：视觉 token 律与参数账用 processor 在 CPU 实测签收（不需要权重与 GPU）；执行侧（阶段计时/显存）交付可执行对照脚本，标未测。

13.1 一次图文请求的五个阶段 ​

text
① 媒体预处理    resize/patch 化 → 视觉 token 数在这里定死（processor）
② 视觉编码      vision tower（ViT 24 层）过每个 patch（注意：按 merge 前的 patch 计，见 13.3）

④ 语言 prefill  整段（文本 token + 视觉 token）一次前向，KV 一次写入
⑤ decode        与纯文本完全同形——视觉 token 只存在于 prefill 写下的 KV 里

两个结构性事实先立住。其一，图像的成本入口是①不是②：分辨率、图数、帧率在预处理阶段就换算成了确切的 token 数，后面每一阶段的账都能从这个数推出来。其二，视觉 token 就是语言 token：模型眼里没有"图"这个对象，只有一段被打上 <|image_pad|> 的序列——第 4 章的 KV 账、第 9 章的调度、第 5 章的量化对它们一视同仁。这正是"迁移应用"的含义：前文全部机制知识直接可用，新增的只有"token 怎么算出来"这一段。

13.2 视觉 token 三笔账（processor 实测，公式双算一致） ​

分辨率律。AutoProcessor 在 CPU 上对合成图实测（本机已跑，raw.json）：

输入像素smart_resize 后grid（t,h,w）视觉 token
64×64256×256（触发下限）1,16,1664
448×448448×4481,28,28196
896×896896×8961,56,56784
1000×333992×320（round 到 32 倍数）1,20,62310
2048×20482048×20481,128,1284,096
6000×60004096×4096（触发上限）1,256,25616,384

公式与实现逐条对上：token = ⌈W′⌉₃₂/32 × ⌈H′⌉₃₂/32（像素 round 到 32 的倍数——patch 16 × merge 2），面积下限 65,536 px（=64 token）、上限 16,777,216 px（=16,384 token）。手算 1280×960：1280/32=40、960/32=30 → 1,200 token，与处理器输出一致。

图像数量律：1/2/4 张 896×896 → 784/1,568/3,136，严格线性（模板与标记另加约 8–14 个文本 token）。多图没有摊薄，只有叠加。

视频帧采样律（实测 10 点全过）：采样帧数 = clamp(int(N/fps_in × 2), 4, 768, N)（目标 2 fps，temporal_patch_size=2），token = round(采样/2) × ⌈W/32⌉ × ⌈H/32⌉。48 帧 704×1280（2 秒）→ 采样 4 帧 → 1,760 token；1 分钟 24fps（1,440 帧）→ 采样 120 帧 → 52,800 token。口径注意：transformers 5.22.1 的视频处理未实现官方 qwen-vl-utils 的每帧像素上限（运行时警告，v5.22 起默认 cap）——与官方工具的数字可能不同，报账先说口径。

13.3 成本落在哪：视觉塔、语言 KV、预处理是三本账 ​

参数账（meta-device 精确计数，不加载权重即可复跑）逐项闭合：总参 4,437,815,808（与模型卡发布数逐位一致）；视觉侧 415M（ViT blocks 302M + merger 27M + DeepStack 三个注入 merger 82M）、语言侧 4,022M（36 层 × 100,930,816 + embed 389M）；attn/层 26,214,656 与手算公式 26,214,400+q/k-norm 256 精确相等——第 2 章的参数算术原样搬到 4B 模型上成立。

把固定样例的三笔账摆开（bf16，账本推演口径；FLOPs 的线性项与注意力二次项分开报，视觉塔按 merge 前的 patch 数计——spatial_merge_size=2，patch 数 = token 数×4）：

样例L_in（vis tok / patch）视觉塔 FLOPs（线性+二次）语言 prefill FLOPs（线性+二次）语言 KV（整段 / 仅图像）
纯文本（32 tok）32（0/0）00.26 T4.7 MB / 0
单图 896×896824（784/3,136）1.90 + 0.97 = 2.87 T6.63 + 0.40 = 7.03 T121.5 / 115.6 MB
双图 896×8961,610（1,568/6,272）3.79 + 3.87 = 7.66 T12.95 + 1.53 = 14.5 T237.4 / 231.2 MB

三个读数直接决定 13.4 的取舍方向：

  1. 图像的执行成本大头在语言侧：单图时视觉塔 2.87 T vs 语言 7.03 T（约 1:2.5）——0.4B 的塔过 3,136 个 patch，4.0B 的主干过 824 个 token，两对比值相乘（参数 1:10 × token 3.8:1）就是 FLOPs 比。"优化视觉编码器"只作用于小头。
  2. 视觉塔的二次项增长更快：双图时视觉注意力二次项 0.97→3.87 T（patch 数平方），占比从 1/4 升到 1/2——图越多、分辨率越高，视觉塔越接近主要矛盾，但没有哪个配置下"只优化视觉塔"就够。
  3. 图像的真实大头在语言侧的 KV：147,456 B/token（2×36 层×8 KV 头×128×bf16）——一张 896×896 的图 = 784 token = 115.6 MB（等价于约 2,700 字的文档上下文；整段输入含模板共 121.5 MB）；第 4 章的 KV 账公式一个字都不用改。

预处理开销（①）是毫秒级 CPU/PIL 工作，只有极高并发或超大图才显著——但它决定后面所有账的形状，这就是"预算在入口定死"的含义。

复用前文知识（13.3 的落点）：量化——KV 账被视觉 token 撑大 147KB/token，KV 量化（第 5 章 5.3 的分布差异）在图文负载上收益被放大；批处理——第 9 章连续批对图文混合负载照常工作，但 token 预算必须按"文本+视觉 token 合计"计算，一条带图请求顶几十条短文本请求的槽位；精确缓存——多轮图文对话共享系统提示与历史图（第 4 章前缀复用），同一图重复提问命中整段视觉 KV。

13.4 阶段时间线：先改输入预算、调度还是执行 ​

三本账的大小关系给出决策次序（执行侧数字在有 GPU 环境按 run_stage_comparison.py 实测核验，本机未测）：

  1. 先改输入预算（通常是它）：降分辨率/限图数/降帧率直接按 13.2 的公式省钱——分辨率减半 = token 减 3/4 = KV 减 3/4，还把视觉塔的二次项（平方增长）一并压掉。判断依据：TTFT 里 prefill 占比 × 视觉 token 占比。质量代价用固定样例看住：判分规则锚定"文字关键词 + 图中小目标字段"（本书实验集用合成图自带 ground truth——24px 小图形画在指定象限，小目标清点要求多组命中且错误断言必须判负，输出存档供人工复核），优化对照一律固定图文任务与判分后再比——对照脚本提供 --image-size 单变量入口（同任务只改分辨率）。
  2. 再改调度：视觉 token 挤占 token 预算与 KV 容量时长 prefill 干扰 decode——第 9 章分块 prefill 与两本预算原样适用；判断依据：带图请求在场时短文本请求的 TPOT 尾延迟。
  3. 最后改执行：语言侧占 FLOPs 约 7 成（单图），融合/图捕获（第 8 章）优先作用在语言主干与 decode 路径；视觉塔只在多图高分辨率（二次项过半）时才值得单独优化——判断依据：trace 里各阶段占比，不凭感觉。

验收对照基准条款：在同一服务上完成文本/单图/多图对照、只改一个输入或运行参数——对照脚本已交付（阶段计时 + 显存计量 + 判分框架），执行实测标未测（5.3，复现条件在 README）；阶段时间与显存用于成本拆解——CPU 侧可拆的部分已拆（token 账实测、参数账精确闭合、三笔成本账推演）；若作优化对照则固定图文任务与判分规则——样例集与判分器随脚本交付（小目标全组命中、否定陷阱、代理判据边界声明）。

降级声明（5.3）：本机无 VLM 运行环境——视觉编码/语言 prefill/decode 的执行时间与显存未测，不冒充实测；processor 实测部分（token 律/参数账）不依赖权重与 GPU，如实签收；不设视觉 token 剪枝综述（1.2 边界）。

练习与答案 ​

练习 1：手算 1280×960 与 1920×1088 两图的视觉 token 数；4K 图（3840×2160）是 720p（1280×720）的几倍？答：1280/32=40、960/32=30 → 1,200；1920/32=60、1088/32=34 → 2,040。4K：round(2160/32)=68 → 120×68=8,160；720p：round(720/32)=22 → 40×22=880——约 9.3 倍（像素面积 9 倍 + 取整效应）。token 数 ∝ 像素面积，"换个大图"在 token 账上是乘法。

练习 2：两张 448×448 的图和一张 896×896 的图，哪个更贵？答：token 上 2×196=392 vs 784——单张 896 的面积是单张 448 的 4 倍（784 = 4×196），所以一张 896 恰好抵两张 448 还贵一倍。KV 与语言侧随 token 线性；视觉塔二次项大图更亏（单图 3,136 patch 的平方 vs 两图各 784）。多图比较类任务用小图分摊，省一半。

练习 3：60 秒 24fps 的 704×1280 视频 token 数？它撑爆了什么？答：采样 = int(1440/24×2)=120 帧（未触 768 上限）→ t=round(120/2)=60 → 60×880=52,800 token（公式外推，实测点到 N=240 截止）；KV = 52,800×147,456 B ≈ 7.8 GB——一条视频请求吃掉一张 24GB 卡三分之一的 KV 预算（还没算权重），第 4 章容量公式换量级后原样成立。这就是视频理解服务必须限时长/降 fps 的算术。

练习 4：视觉塔与语言主干的参数比是 0.415B:4.0B（≈1:10），为什么单图的 prefill FLOPs 比只有约 1:2.5？答：FLOPs 比 = 参数比 × token 数比——视觉塔过的是 merge 前 3,136 个 patch（token 的 4 倍），语言主干过 824 个 token：0.415×3,136 ≈ 1,302 vs 4.02×824 ≈ 3,314，比值 1:2.5。两个"看起来小"的因素（塔小、但 patch 多）相乘后差距收窄；再叠上注意力二次项（视觉 patch 数平方），双图时视觉塔占比升到 1/2。推论不变但更精确：压缩视觉 token（降分辨率）同时省两段，优化视觉塔算子只省小头且只在多图高分辨率时值得。

练习 5：图文服务要做 KV 量化与连续批处理，各要注意什么？答：KV 量化（第 5 章口径）收益被视觉 token 放大（147KB/token），但要复验小目标质量——量化误差在注意力分布上的扰动对细粒度视觉定位更敏感，判分规则必须含小目标字段且错误断言判负；连续批处理照常工作，但 token 预算与 KV 容量要按"文本+视觉 token 合计"计——一条 896×896 带图请求（824 token）≈ 82 条 10 token 短请求的预算占用，调度不公平会饿死文本请求（第 9 章两本预算的图文版）。

练习 6：判分规则里小目标样例为什么要求"全组命中"而文本问答只要求"任一组"？答：小目标检查的失败模式是漏看（答了红和蓝、漏了黄）——任一命中就放行会把"只看见最显眼图形"的退化当通过；文本问答的判据是"说到了要点"，关键词组是同义改写（复用/保存/留着），任一组命中即达标。两条规则都锚定任务事实、都是代理判据（第 5 章口径：能挡多数退化，语义反转仍需人工检视，输出存档备查）。

小结：算了什么、慢在哪里、怎样验证 ​

  • 视觉 token 律三条全实测：分辨率（⌈·⌉₃₂ 相乘，64..16,384 边界）、图数（线性）、帧采样（clamp(int(N/fps_in×2),4,768,N) × 每帧 token）——入口预算由 processor 定死，手算与实测逐点一致；
  • 三本账分清：图像执行成本大头在语言侧（单图 FLOPs 约 1:2.5、双图升到 1:1.9——视觉塔二次项随 patch 数平方增长），KV 大头在语言侧（147,456 B/token，一张 896² ≈ 115.6 MB）；预处理本身毫秒级但决定一切；
  • 决策次序：输入预算（线性省 KV + 平方压二次项，质量用固定样例+小目标判分看住）→ 调度（图文合算 token 预算，分块治干扰）→ 执行（优先语言主干；视觉塔只在多图高分辨率时单独值得）；
  • 验证改动的方法：token/参数账公式与实测双算（断言）、参数逐组件闭合（模型卡数字逐位对上）、执行侧脚本就绪标未测（复现条件写明、单变量入口 --image-size）。
