第 9 章 · 批处理与请求调度 ​

到此为止，全书实验都是"一条请求"。真实服务同时面对几十上百条：有的 prompt 三个 token、有的三千；有的生成 8 个 token 就停、有的要写满 2048。本章的问题是：多个请求抢一份计算资源时，谁来决定下一步算谁的 token？这个决定付出什么代价？

答案是一片被称调度的设计空间：静态批、连续批、分块 prefill。配套实现 pi_infer/scheduler.py（简化调度器：真实逐请求前向保证输出正确 + 实测单位成本计费模拟时间轴），实验 experiments/exp_ch9_batching/。

先声明计时口径（评审定下的纪律）：调度器的时间轴是**"实测单位成本的离散事件模拟"——每个迭代的 decode 步成本与 prefill 块成本来自启动时对本机 tiny 模型的实测（bench 纪律：预热、交错重复），混合迭代按串行相加计费、活动 batch 钉在实测上限 8 以内不外推。下文所有延迟指标都叫模拟 TTFT/TPOT**——它们支撑机制对照（谁比谁大、为什么），不是服务或设备实测延迟（5.3）。

9.1 静态批：最朴素的组批与它的浪费 ​

批处理的第一直觉：batch 维把多条请求的同一层矩阵乘堆成一个大 GEMM（第 3 章练习 5：算术强度随 batch 上升）。最简单的做法是静态批——攒够 N 条（或等到超时）一起算，全部完成再接下一批。SchedulerConfig(policy="static") 的实测（同一 32 条请求的固定到达轨迹）：

text
static:      模拟吞吐 8434 tok/s，p50 模拟 TTFT 34.6 ms
continuous:  模拟吞吐 12577 tok/s，p50 模拟 TTFT 17.9 ms   ← 同一轨迹、同一模型
1
2

差距 1.5× 从哪来？静态批的两个结构性浪费，完成时刻表（scheduler_raw.json）里看得见：

  1. 槽位搁浅：批内 8 条请求长短不齐，先完成的请求槽位空转——调度器记了 static_stranded_slot_seconds（搁浅槽位×持续时间的积分），直到全批完成才能换人；
  2. 到达错峰：批开始后新到的请求只能干等下一批——它们本来可以立刻填进空槽。

**迭代组批（iteration-level scheduling）**是解法：调度的粒度从"一批请求的一生"细化到"一次模型迭代"——每个 iteration 结束时，完成的请求立刻退出、排队的请求立刻补位。Orca 把它带入 LLM 服务并给出配套的 selective batching（只对选定算子做批处理以兼容变长，S29）；这是"连续批处理"（continuous batching）的机制内核。本书调度器的 policy="continuous" 实现同一思想——每个 iterate() 重算本迭代的成员。

9.2 连续批处理：状态机与两本预算 ​

连续批处理的世界里，一条请求是一个状态机：

text
waiting ──入批──▶ running ──生成完──▶ finished
   ▲                │
   │           cancel / fail
   └──── 统一回收路径（第 4 章 release(reason) 的同一约定）
1
2
3
4

调度器每个迭代做的事（pi_infer/scheduler.py::iterate）：决定谁入谁出 → 组成本迭代的计算（prefill 块 + decode 步）→ 执行 → 记账。约束它的是两本预算：

  • token 预算：本迭代输入 token 总量上限（decode 每请求计 1）——直接对应一次前向的 batch×长度，守住设备单步规模；
  • KV 容量：第 4 章的账在此落地——每条 running 请求预留 prompt + max_new − 1 个 KV 槽（与生成契约一致：最后一个生成 token 尚未入缓存），容量不足时请求保持 waiting 而不是被丢弃。

正确性判据（验收原文"不丢请求、不串状态"的落地）：调度器驱动下每条请求的输出与逐请求独立运行 greedy_decode 的受控参考逐 token 一致——三种策略全部 32/32 一致（实验 PASS）。调度改的是"何时算"，永远不许改"算出什么"。取消与失败走同一回收路径、预留 KV 全额归还、重复取消报错——第 4 章的纪律原样搬进调度层。

9.3 长 prefill 的干扰与分块 ​

连续批解决了换人问题，但还有一类干扰：不受逐迭代预算约束的引擎里，一条 3000 token 的 prompt 会独占一次大计算，期间批内其他请求的 decode 全部停摆——长 prefill 拖累短请求的 TPOT。Sarathi-Serve 的解法是 chunked prefill：把长 prompt 切成近等大的块，每迭代只塞一块进 batch，stall-free 地"边 prefill 边 decode"（S24）。先看清前提差异：本调度器的 continuous 本身已是混合迭代、且 token 预算（9.2）就是每迭代 prefill 上限——分块"从停顿到混合"的收益在此不存在，下表如实呈现的是只剩代价的一面。

policy="chunked", chunk_size=C 的实测（同一轨迹，终验复跑值）：

策略模拟吞吐p50 模拟 TTFTp99 模拟 TPOT
continuous（不分块）12,577 tok/s17.9 ms0.77 ms
chunked C=3211,737 tok/s20.4 ms0.77 ms
chunked C=169,952 tok/s27.0 ms0.82 ms

读数方向如实读：块越小，三项越差——TTFT 27.0 vs 17.9 ms（prefill 切得更碎，新请求要等更多轮）、吞吐 9,952 vs 12,577（小 GEMM 效率差）、TPOT p99 0.77→0.82 ms 也没有改善：本调度器的 continuous 已把 prefill 与 decode 混在同一迭代，分块换不来"解除停顿"的收益，只剩代价。机制收益依赖前提：Sarathi-Serve 的 decode 保护与容量收益（2.6–3.7×，S24）出现在"长 prompt 独占迭代"的系统里；本模拟前提（混合迭代 + 预算封顶）下，C=32 相对 continuous 的 −6.7% 吞吐就是纯代价。C 怎么选仍是吞吐与尾延迟的取舍，且先要确认前提成立：长 prompt 占比高、引擎允许独占迭代、SLO 押 TPOT 尾延迟时，分块才可能用 TTFT/吞吐换 decode 节奏——第 15 章容量曲线与 --max-num-batched-tokens 旋钮会再遇到它。

9.4 吞吐—尾延迟曲线，与一个经典误用 ​

容量问题问的是：这台服务最多每秒吃多少请求还能守住 SLO？ 答案不是一条数字而是一条曲线：固定请求分布，扫描到达率，看 p99 延迟何时破线。画曲线时有一个能悄悄骗过所有人的坑——客户端发压不足：

客户端并发只有 4 时，服务端最多同时看到 4 条在途请求——你测到的"最大吞吐"其实是客户端的上限。把客户端并发加到 32，"最大吞吐"跟着涨——这说明之前测到的根本不是服务容量。

实验复现（run_underload_experiment.py，同一服务配置、同一目标到达轨迹，只改客户端并发 K）：

K观测峰值模拟吞吐最大服务端等待模拟排空时长
49,984 tok/s3 条0.010 s
3216,848 tok/s24 条0.056 s

三列一起读才是完整的诊断：K=4 时服务端等待最多 3 条——服务常常闲着等客户端；K=32 时等待 24 条——服务真正吃满，排空时间随之变长（0.010→0.056 s）。判定容量时的三条纪律（验收原文的落地）：对照目标到达轨迹与实际发出时刻（发压不足时两者分离，分离量就是被客户端吞掉的到达）；看积压深度（服务饱和的标志是积压持续增长而非波动）；停压后看排空（积压能在合理时间排空说明系统稳定过载，排空时长随负载增长）。实验里 K=4 的"吞吐"若被当成容量，会低估约四成（41%）。

生产引擎对照：vLLM 的连续批处理即 9.1–9.2 机制的工业实现（iteration 级调度 + paged KV 的 token 容量），启动与压测命令按官方文档登记于 experiments/exp_ch9_batching/（S3；本机未装 vLLM，未实测——第 15 章部署包登记了一键复现条件，引擎侧同样标未测）。本章机制结论不依赖特定引擎。

验收对照基准条款：简化调度器完成（三策略可配、token 预算与 KV 容量约束）；长短混合负载比较静态/连续组批及分块配置（9.1/9.3 数据）；"不丢请求、不串状态"以逐请求独立运行的受控参考逐 token 一致为判据（32/32 PASS；模拟数字随单位成本实测波动——同机各代复跑吞吐相差百分之几、跨环境可达两成量级，正文统一引用终验干净环境复跑值，以 raw.json 为准）；负载脚本固定到达轨迹并记录实际发出时刻、积压与排空（9.4 表）；失败/取消请求全部入账（counts 全列、无隐藏）。

练习与答案 ​

练习 1：静态批 8 条请求，生成长度 {8,8,8,8,48,48,48,48}。搁浅槽位比例大约多少？答：静态批要等最长的跑完——总槽·步 = 8 槽×48 步 = 384，其中有效 = 4×8+4×48 = 224，空转 = 4×40 = 160，160/384 ≈ 42%。生成长度方差越大，静态批越亏；全长相同时零浪费——负载画像决定批策略收益。

练习 2：token 预算 128、当前 batch 8 条 decode 各占 1，新请求 prompt 200。连续批怎么处理它？答：本迭代 8 个 decode 占 8，余 120 给 prefill——200 的 prompt 装不下，这个迭代不收它（或收进来只 prefill 120？——取决于实现是否允许 prefill 跨迭代续传）。本书调度器允许跨迭代续传（_prefilled 记进度）；若实现不允许，200>120 的请求会永久饿死——预算小于最大 prompt 的调度器必须支持分块续传，这是 9.3 分块的另一个存在理由。

练习 3：9.4 里 K=4 时"最大服务端等待 3 条"说明了什么？K=32 时 24 条又说明什么？答：K=4：服务端经常空转等客户端（等待数 ≤3 且短），瓶颈在客户端——测到的吞吐是客户端并发×单请求速率，与服务容量无关；K=32：等待队列持续深（24 条），服务饱和——这时测到的才是服务侧容量。诊断口诀：先确认瓶颈在谁那里，再谈容量数字。

练习 4：9.3 表里把 chunk 从 32 降到 16（token 预算不变），p99 模拟 TPOT 从 0.77 变 0.82 ms（差 6.5%）、p50 模拟 TTFT 从 20.4 坏到 27.0 ms（+32%）、吞吐 11,737 掉到 9,952。这组数据支持"调小块"吗？答：不支持——本调度器的 continuous 已是混合迭代且受预算约束，分块的 decode 保护收益（S24 的场景：长 prompt 独占迭代、decode 停摆）在此前提不成立，调小只剩代价。什么时候才可能值：引擎允许长 prompt 独占迭代、SLO 押 TPOT 尾延迟且长 prompt 占比高——前提变了，取舍方向才可能变（第 15 章 --max-num-batched-tokens 就是这个旋钮；"容量可行/吞吐可接受/单请求低延迟是三件事"的第 12 章预告照旧成立）。

练习 5：为什么调度器正确性判据用"逐 token 与参考一致"而不是"输出统计相同"（如平均长度、词频）？答：调度层最常见的 bug 是串状态（A 的 token 喂进 B 的缓存）——它可能只让某一步分叉、输出仍"看起来像话"，统计指标完全发现不了；逐 token 对照能在分叉的第一个 token 就暴露。这与第 4 章四组合一致、第 7 章回滚检查是同一条铁律：正确性判据选最严的，性能指标才配谈取舍。

小结：算了什么、慢在哪里、怎样验证 ​

  • 批的账：batch 把权重搬运摊给多条请求（算术强度×B），静态批因槽位搁浅与到达错峰浪费（实测 8,434 vs 12,577 模拟 tok/s）；迭代组批把调度粒度细化到一次模型迭代，Orca 称 iteration level scheduling + selective batching（S29）；
  • 两本预算（token 预算/KV 容量）约束每个迭代；分块 prefill 用 prefill 效率换 decode 节奏（C=16/32 实测取舍），Sarathi-Serve 的 chunked prefill/stall-free 同源（S24）；
  • 容量测量三纪律：目标到达 vs 实际发出、积压深度、停压排空——发压不足会把客户端上限冒充服务容量（实测 9,984 vs 16,848，低估约四成）；
  • 验证改动的方法：调度正确性=逐 token 与受控参考一致（32/32），调度性能=模拟指标只做机制对照。
