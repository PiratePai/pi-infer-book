第 7 章 · 投机解码：MTP、DSpark 与 DFlash 1/2 ​

第 4 章把"每步只算一个新 token"变成了可靠的基础设施，但串行依旧：每个 token 都要等一次完整前向。本章的问题是：能不能一次前向拿回多个 token？ 思路是"先猜后验"——用一个便宜的提议者猜出一段候选，再用目标模型一次前向同时验证整段，猜对的部分直接提交，猜错的位置修正并回滚状态。

这不是近似解码：贪心口径下投机解码与逐 token 贪心逐位一致，采样口径下保持目标分布（7.1 证明）。收益全部来自"验证 k 个草稿只需一次前向，接受 m 个就赚 m−1 次前向"。代价同样清晰：草稿本身要花时间，猜错的位置白算还要回滚——投机是一场关于接受率的成本交易，本章把它算清楚。

四条实现路线共用一套验证骨架：MTP 把提议者挂在目标模型上（7.2），DSpark 用半自回归结构建块内依赖并以置信度调度验证（7.3），DFlash 1/2 用块扩散模型一次前向并行起草（7.4）。配套实现 pi_infer/speculative.py，实验 experiments/exp_ch7_speculative/。

7.1 公共骨架：提议 → 验证 → 接受 → 修正 → 回滚 ​

五段式骨架对 MTP、DSpark、DFlash 全部成立，差异只在"提议者怎么来"。pi_infer/speculative.py::verify_and_accept 是可运行的最小版本：

  1. 提议：draft_fn 产出候选 token 及其分布 draft_logits（提议者认为自己对的概率 q）；
  2. 验证：目标模型对 prompt + 草稿 做一次全量因果前向，每个草稿位置得到真分布 p（一列 logits）；
  3. 接受：贪心口径——token == argmax(p) 即接受；精确采样口径——以 min(1, p/q) 接受；
  4. 修正：首个拒绝处，贪心取 argmax(p)，采样从归一化残差 max(0, p−q) 重采一个；
  5. 回滚：接受前缀之后的 KV 一律截断（truncate_to），修正 token 重新前向写入。

先手算一次精确采样（S1 实验，raw.json 可对）。设词表只有 {0,…,31}：

text
p 支撑 {0, 16}：p(0)=0.4, p(16)=0.6
q 支撑 {0, 24}：q(0)=0.55, q(24)=0.45
草稿本次抽到 token 0
1
2
3

接受概率 = min(1, p(0)/q(0)) = min(1, 0.4/0.55) ≈ 0.728。若拒绝，残差 r = max(0, p−q)：r(16)=0.6 是唯一正项（p(0)−q(0)<0 归零），修正 token 必然是 16。S1 用 2000 次固定种子采样验证：实测接受 0.732、拒绝后修正落在 16 的频率 1.0——手算、代码、统计三方对上。这两条规则（接受 min(1,p/q)、拒绝从 norm(max(0,p−q)) 重采）正是 Leviathan 等人给出的 speculative sampling 定义，且可以证明如此采出的边缘分布恰好等于 p（S16 附录 A.1）——"分布保持"不是近似。

区分三种"对"，验收时不得混谈：greedy 一致（逐 token 与贪心严格相同）、分布保持（理论上边缘分布等于目标）、有限测试数值接近（统计检验不拒绝）。本书所有对照实验用第一种作判据、第二种作原理、第三种如实报告样本量。

7.2 MTP：从主干特征预测下一个 token ​

MTP（multi-token prediction） 的提议者不是另一个小模型，而是挂在目标模型上的一个预测头。DeepSeek-V3 给出的结构（S17，式 (21)）：第 k 个预测深度把主干（或上一层 MTP）的特征 h 与下一个输入 token 的 embedding 拼接、各自 RMSNorm 后线性投影，过一个 Transformer 块，接共享的输出头；逐深度保持完整因果链。训练目标是多预测一位，推理时可以整个丢弃 MTP 头，也可以把它转用作投机解码的草稿器——DeepSeek-V3 报告第二 token 接受率 85–90%、配合投机解码 1.8× TPS（S17）。

两件事必须分开（本章最容易混的点）：

  • 训练时"预测多个位置"：MTP 头以"看过前缀、预测下一位置之外的第二位置"为目标，学到的是利用主干特征的超前预测能力；
  • 推理时"验证后提交多个 token"：无论 MTP 头多准，它给的 token 仍是草稿，必须过 7.1 的验证。猜错不修，输出就不是目标模型的输出。

两个对齐期撞见的checkpoint级事实值得记录（8 组合扫描在 mtp_raw.json）：fc 输入顺序是 embedding 路在前——与 DeepSeek-V3 报告的书写顺序（hidden 在前）相反，换序后教师一致率 9/18→0/18；MTP 层是全注意力且必须整段因果前向携带历史，单 token 前向接受率 0/12。书面公式与 checkpoint 实现可能不一致，以权重直查为准——这是"加载匹配的 target/draft"（7.5 第 1 条）的实证。

成本模型。把投机当成一笔交易来算（S16 定理 3.8）：设草稿/目标单步成本比为 c、逐位接受率为 α、草稿长 γ，每轮期望提交 token 数为

E[tokens]=1−αγ+11−α(α=1 时为 γ+1),墙钟改进上界=E[tokens]γc+1

注意分母 γc+1：草稿不免费。本书 speculative_generate 的实现口径在全接受时不追加 bonus token（下一轮的验证前向承担该角色），对应期望提交数 =1−αγ+11−α−αγ，即 ∑i<γαi。两个口径都要会算——7.6 的第一个问题（指标混谈）从这里开始。

7.3 DSpark：半自回归提议与置信度调度 ​

MTP 的草稿器在推理时仍是顺序的：每多猜一位，要么多过一次草稿器（MTP 链），要么接受率随深度快速衰减。DSpark（S18）把提议改成半自回归：一个并行主干一次算出整块候选，再由轻量顺序模块在块内补依赖——

  • 并行主干 + 轻量顺序模块：块内 token 位置可以并行计算（省串行步），但完全并行的提议"各猜各的"，token 间没有依赖，接受率随块内位置快速衰减（论文称为 suffix decay，后缀衰减）；顺序模块用很小的工作量把"前一个 token 是什么"的信息重新注入，抑制衰减；
  • 置信度调度验证：不是每个草稿都值得验证。DSpark 给每个草稿 token 估计接受概率，按"前缀存活概率"（接受是前缀事件——第 i 位被验证当且仅当前 i−1 位都活了）与引擎的吞吐画像（当前并发下每 token 验证成本）动态决定验证到多长；
  • 工程数字（DeepInfer 部署问答，S20）：草稿一次出 5 个 token，按置信度排序取前缀子集送验证；相对固定验证 5 个，每步验证 token 约省 30%（5.00 → 3.2–4.4）而接受长度基本不变（3.29 vs 3.20）；并发 60 的生产工作点吞吐 +4–7%（并发 16 时 −1.5%、96 时 +11%——收益随并发变化，不是常数）；论文口径下对生产基线 MTP-1 等吞吐每用户提速 60–85%（S18，DeepSeek-V4 系统）。

对照 7.2 的成本模型立刻能看懂它在优化哪一项：γ 不再是固定值，而是"按置信度动态截断"——把验证预算花在存活概率高的前缀上，分母（验证成本）压小、分子（期望提交）几乎不损失。DeepSpec 仓库（S19）提供了 DSpark/DFlash/EAGLE-3 三种草稿器的训练与评测代码和 checkpoints（目标 Qwen3 4B/8B/14B 与 Gemma，checkpoint 命名如 dspark_qwen3_4b_block7——块大小 7）。

7.4 DFlash 1/2：并行块起草与候选选择 ​

DFlash（S21，ICML 2026）代表另一条提议路线：草稿器是一个轻量块扩散模型，一次前向并行产出一块候选 token，且以目标模型的上下文特征为条件——提议质量来自"看得见目标看到的东西"。验证骨架与 7.1 完全相同（lossless：拒绝采样保证输出分布不变），论文报告 >6× lossless 加速、较 EAGLE-3 至多 2.5×。

它的代价也在 7.2 的公式里：并行起草省了草稿器的串行步（c 变小），但块内没有顺序依赖——候选间依赖不足，块越长后缀衰减越重。这正是差异对照表里 DFlash 1 那一行的意思：并行提议省了什么（草稿延迟）、影响什么（接受长度）。

DFlash 2（官方工程说明，S23）针对两个具体痛点做了增量改进。注意表述边界：这是 2026-08 的厂商工程博客，不是同行评审结论，其中基准为厂商自报：

  1. 候选选择："正确的 token 通常在候选列表里，只是不在第一位"——DFlash 2 每位置保留 top-16 候选，用一个低秩双线性注意力选择器给相邻位置候选组合作打分（口号是"选择比预测便宜"，Choosing is cheaper than predicting）；
  2. 局部依赖：后缀衰减"大部分是局部问题"——在注意力和 MLP 子层旁加两抽头动态深度卷积，让信息在块内跨位置流动，而所有位置仍然并行计算。

自报数字：每轮验证多产出 16–25% token，代价约 +1.3% 周期延迟与 +3% 参数；吞吐 2.7–3.4×（Qwen3.8-27B、batch 1、SGLang）。工程入口：z-lab/dflash 仓库（S22，MIT）提供 pip install dflash、HF checkpoints 与 OpenAI 兼容服务接入（SGLang/vLLM 等）。正文引用这些数字时一律标注口径——它们是厂商自报基准，未获正式会议结论背书。

7.5 工程验证：上真实模型前查五件事 ​

任何 target/draft 组合，投机开跑前的检查清单（每条都有对应实验）：

  1. 验证骨架的边界（S2，全绿）：全接受、位置 0 拒绝、中间拒绝+修正后继续、草稿中间命中 eos 停止、拒绝回滚后 KV 长度与后续输出同贪心对照一致；
  2. 模板与词表：draft 与 target 必须同 tokenizer 同 chat template——MTP 实验中草稿 embedding 直接来自目标模型 embed_tokens（mtp_use_dedicated_embeddings=false），从结构上消除这类错配；外挂草稿模型（DeepSpec 训练的 DSpark/DFlash 头）时逐项检查；
  3. 采样口径：贪心对照用 greedy=True；采样对照固定同一 RNG seed 与同一温度/top-k——p/q 必须同口径处理，否则 min(p/q) 无意义；
  4. 缓存与回滚路径：验证用缓存必须支持 truncate_to（verify_and_accept 对不支持的实现提前报错）；分页缓存下回滚切入共享块时写时复制（第 4 章 4.5）；混合主干的循环状态没有"截断"语义（第 4 章 4.2）——快照或全量重放，本章实跑选后者；
  5. 负载成本：记录每轮接受长度、草稿/验证时间、峰值内存——接受长度好看但草稿更贵时，端到端反而变慢（7.6 第一条的实证）。

7.6 当前存在的问题 ​

把本章实测与四条路线的公开数字放回 7.2 的成本公式，四个问题浮出来：

  1. 接受长度、接受率与墙钟收益是三个指标。扫描里 oracle 的 α=1.0、每轮提交 3.0，墙钟却只快 1.5×；MTP 实跑接受 8/12 也只有 1.26×。接受长度是分子，提议成本、验证变长、拒绝后重算都在分母——DSpark 的置信度调度（S20：省 30% 验证 token、接受长度几乎不变）优化的正是分母。只报接受率不报分母，是这类文章最常见的修辞。并行提议还受依赖质量、词表投影与验证成本限制——DFlash 1 的后缀衰减就是"并行省了草稿时间、输掉了接受长度"的平衡被打乱。
  2. 候选长度与并发、上下文、硬件耦合。S20 的三点数据（−1.5%/+4–7%/+11%）说明同一配置在不同并发下收益不同；低并发下快的长草稿在高并发会挤占批量容量、拖累短请求尾延迟——第 9 章的调度视角会再遇到它。
  3. 分布匹配是条件不是属性。草稿与目标的领域、模板、精度或采样口径不匹配时，接受表现要重测；本书噪声草稿实验（ε 从 0.5 到 2.0，α 从 0.23 掉到 0.02）是"匹配度决定一切"的受控版本。不把某一位置的接受趋势当普遍定律。
  4. 回滚正确性不能靠平均速度发现。7.2 的修正重算案例：不重算时输出从第 5 个 token 起崩坏，而平均每 token 时间看起来毫无异常。混合状态（循环状态无截断语义）、前缀缓存共享块（写时复制）、结构化输出（约束只作用在提交 token 上）都让回滚路径更容易错——判据永远是"拒绝后逐 token 对照"，不是速度。

7.7 未来发展方向 ​

围绕 7.6 的四类问题，工程上有三类改进方向。每类说清：想改善什么、付出什么、怎么检验——不预测哪条路线胜出。

① 按负载与测得成本调整提议/验证预算。DSpark 的置信度调度是这个方向的代表：动态决定验证长度，而不是固定 γ。要改善的是 7.6-1/2 的分母与并发耦合；要付出的是置信度估计本身的开销与调度复杂度（S20 里 CPU 调度只定总量、每请求长度在 GPU 端重算，就是为了不把这块成本加回关键路径）；检验方法是固定负载扫描并发与 γ，报告接受长度、验证 token 数与尾延迟三列——只有前两列变好不算数。

② 以较小开销改善块内依赖与候选选择。DFlash 2 的两个部件（top-16 选择器 + 两抽头卷积）自报 +16–25% 提交、+1.3% 延迟、+3% 参数；DSpark 的轻量顺序模块同理。要改善的是并行提议的后缀衰减；要付出的是草稿器变重（c 上升）与训练/维护成本；检验方法是同一验证骨架下做消融——单独开选择器、单独开依赖模块、全开，各报接受长度与端到端（厂商自报数字在同行评审与独立复现前按 S23 口径对待）。

③ 统一状态回滚、兼容性检查与性能退化回退。7.5 的五件事今天是手工清单：模板/词表/采样口径逐项核对、回滚路径依赖缓存实现、混合状态另案处理。改进方向是把它们变成引擎的一等公民——加载时校验 target/draft 组合、每轮投机与关闭投机并行对账、检测到接受率或输出分布异常时自动回退到不投机路径。要付出的是常驻校验开销与"回退"本身的语义设计（在途请求怎么办）；检验方法是注入错配（本书实验已经造得出：换 fc 顺序、错模板）观察检查是否报警、回退是否无损。

练习与答案 ​

练习 1：7.1 手算例中，若草稿抽到的是 token 24（q(24)=0.45，p(24)=0），接受概率是多少？拒绝后修正分布是什么？答：p(24)=0，min(1, 0/0.45)=0——必然拒绝；残差 max(0,p−q) 在 16 处为 0.6、在 0 处 0.4−0.55<0 归零，修正必然是 16。q 有支撑而 p 无支撑的 token 是"纯浪费"：验证概率为 0，这正是 S4 随机草稿接受长度全 0 的机制。

练习 2：用 7.2 的公式算：α=0.8、γ=4、c=0.05（草稿每步是目标的 1/20），墙钟改进上界是多少？γ 改成 8 呢？答：E=(1−0.8⁵)/0.2=(1−0.3277)/0.2=3.36，上界=3.36/(4×0.05+1)=2.80×；γ=8 时 E=(1−0.8⁹)/0.2=(1−0.1342)/0.2=4.33，上界=4.33/(8×0.05+1)=3.09×。草稿翻倍只多了 0.29×——收益对 γ 边际递减、对 α 极敏感：把 α 从 0.8 提到 0.9（γ=4）得 E=(1−0.9⁵)/0.1=4.10、上界 4.10/1.2=3.41×，α=0.9 且 γ=8 时 E=6.13、上界 6.13/1.4=4.38×——接受率是比草稿长度更强的杠杆（DFlash 2 候选选择的动机）。

练习 3：扫描表里 oracle（α=1）墙钟只快 1.5× 而不是理论无穷倍，为什么？答：tiny 上草稿器=目标模型，c=1：上界=(γ+1)/(γ×1+1)=1（γ=3 时 (3+1)/4=1.0，与实测 1.0–1.5× 吻合，超出部分来自拒绝路径省的前向）。公式分母的 γc 项在 c=1 时把分子完全吃掉——这就是 MTP 头必须远小于主干、DSpark/DFlash 必须并行起草的原因。

练习 4：DSpark 为什么要"按置信度排序取前缀子集"验证，而不是"逐个验证直到第一个拒绝"？答：贪心验证本来就是前缀事件（接受到第 i 位才能验第 i+1 位）——但"验到多长"是可选的：置信度低的尾部草稿存活概率按乘积衰减，验证它们大概率白算。排序取前缀=把每步验证预算分配给存活概率最高的子序列。S20 的实测（省 30% 验证 token、接受长度 3.29 vs 3.20 几乎不变）说明尾部草稿的边际收益确实接近零。

练习 5：DFlash 2 的选择器"每位置保留 top-16 候选"，这与投机解码的验证骨架冲突吗？答：不冲突——选择器属于提议阶段，它在草稿分布 q 内部挑选更可能的组合（改变 q 的形状，让草稿更接近 p）；验证与修正仍是 7.1 的骨架，输出分布不变性由拒绝采样保证（S21/S23 均声明 lossless）。任何"提高接受率"的提议侧改动都不需要动验证正确性——这是骨架与提议解耦的好处。

练习 6：你把 MTP 实验的 chat template 换成了另一模型的模板再跑，接受率掉到 1/12 且输出与参考不一致。给出定位顺序。答：先查判据层——输出不一致已经说明不是接受率问题而是正确性问题；按 7.5 清单：②模板/词表错配（prompt token 序列都变了，MTP 看到的条件分布整体漂移）是第一嫌疑；①验证骨架本身没动过可排除；④缓存回滚路径没动可排除。模板属于模型发布的一部分（第 1 章 1.1），换模型必换模板——这个案例里"接受率下降"只是症状，根因是草稿条件分布 q 整体错位。

小结：算了什么、慢在哪里、怎样验证 ​

  • 投机的账：收益 = 每轮期望提交 token 数 ÷ 每轮前向次数（含拒绝重算），成本 = 提议者开销 + 验证变长的前向；接受率 α 是最强杠杆，草稿成本比 c 与候选长度 γ 共同决定分母；
  • 四条路线在同一个骨架上换提议者：MTP（挂载头、顺序、c 小）、DSpark（半自回归 + 置信度调度，把验证预算花在前缀存活概率高的子序列）、DFlash 1/2（并行块起草，用候选选择与局部依赖治后缀衰减）；
  • 慢在哪里没变（仍是目标模型前向），变的是每次前向换回的 token 数；
  • 验证改动的方法：贪心口径逐 token 对照（MTP 实验 PASS）、采样口径统计检验（S1 手算 0.728 vs 实测 0.732）、回滚后输出检查（S2 五边界 + 修正重算案例）、扫描与公式双报（实测提交数 vs 调整公式）。
