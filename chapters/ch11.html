第 11 章 · P/D 分离与 KV 传输 ​

第 9 章的调度器把 prefill 与 decode 塞进同一个实例轮流算；第 10 章把一份模型拆到多卡。本章是第三种拆法：按请求阶段拆实例——prefill 集群专门算 prompt，decode 集群专门逐 token 生成，请求带着它的状态从前者"交接"到后者。本章的问题是：为什么值得拆？交接的对象到底是什么？拆错会出什么事？

配套实现 pi_infer/pd.py（双进程交接骨架：四阶段协议 + 错误路径），实验 experiments/exp_ch11_pd/。本机 CPU 双进程（gloo）实跑签收正确性；真实引擎的 P/D 分离实测未测（5.3）。

11.1 分离动机：先把组内问题解决完，再拆实例 ​

Prefill 与 decode 的资源画像天生相反（第 1/3 章已测）：prefill 是一次性大 GEMM（算力密集、显存带宽吃满），decode 是逐 token 小批（带宽密集、算力闲置）。塞进同一实例，就是第 9 章 9.3 的干扰问题——但先用尽组内手段：连续批处理（9.1）、分块 prefill（9.3）、token 预算（9.2）已经把"长 prefill 打断 decode"压到可控范围。什么时候还不够？

  • SLO 押在两头（TTFT 与 TPOT 同时要紧）：组内调和意味着 batch 组成互相牵制——prefill 突发挤 TPOT，decode 大批挤 TTFT，两个 SLO 抢同一份调度自由度；
  • 两阶段的并行策略最优解不同（第 10 章）：prefill 吃 TP（大 GEMM），decode 吃小 TP+副本——合置时一套并行配置被迫妥协。

DistServe（S25）把这两点形式化：合置导致 prefill-decoding 干扰并耦合了两阶段的资源与并行规划；分离到不同 GPU 后按各自的 TTFT/TPOT 需求分别优化，再按集群带宽决定两阶段实例的放置与配比（分离引入的 KV 传输必须算进账）。它的 goodput-per-GPU 口径（"同时满足 TTFT 与 TPOT 约束的最大服务速率"）是第 9 章容量曲线的双 SLO 版。分离不是通用最优——11.4 的账会给 出反例条件。

11.2 交接对象：恢复推理所需的完整状态 ​

交接的本质问题：**decode 实例拿到什么，才能把这条请求的生成继续下去、且与没分离时逐 token 一致？**对纯注意力（Dense）模型，答案是 KV 缓存。但"把 KV 传过去"这句话里有三个必须写死的约定（pd.py 的消息契约）：

  1. 覆盖到哪个 token：与本书生成契约一致——缓存 KV 长度 = len(token_ids) − 1（最后生成的 token 尚未做前向，第 2 章 greedy_decode 的同一条约定）。D 端首步重喂最后一个 token 取得下一步 logits。差一个 token 的错位，输出就在某个位置静默分叉；
  2. 布局与精度：逐层 K/V 张量 [Hkv, T, D] 的形状、dtype、层序显式随消息声明，重建端逐项校验——不校验的传输是盲传；
  3. 数据量：tiny 交接 T=16 时 8,328 B（512 B/token 的 KV + token 表 + 控制字段），T=128 时 66,568 B——随 T 线性。

混合模型只传 KV 是不够的。Qwen3.5-0.8B 的 GDN 主干（第 4 章 4.2 的账，S0/S4）：全注意力层 KV 12,288 B/token（随 T 线性），线性注意力层另有循环状态——conv state 每请求 1.8 MB + recurrent state 每请求 18.9 MB（fp32，固定、不随 T 增长）。交接一条 T=1,000 的请求：KV ≈12.3 MB，循环状态 ≈20.7 MB——循环状态占 63%，只传 KV 的 decode 端拿到的是一条"失忆"的请求。Dense 交接骨架与混合模型的差异只在"消息里多几段张量"，但恢复语义完全不同（KV 可截断重算尾部，循环状态必须整段快照——第 4 章练习 5 的结论原样适用于交接）。本书按 6.4 边界：混合模型只在账与验收层面涉及（此账 + 验收要求"运行时支持条件"），不做混合模型加载实跑。

11.3 所有权与错误路径：交接协议的四阶段 ​

状态在两个进程间转手，出错的窗口比单进程多一个维度。pd.py 用四阶段协议把每次交接钉死：

P 端                                D 端
Prepare(request_id, epoch, 形状预告)  ──▶  预留/校验
Data(request_id, epoch, tokens, KV)  ──▶  校验约定 → 重建缓存
                                    ◀──  Ack(request_id, epoch)     ← 所有权转移点
（此后 P 不得再动这条请求的状态）
Commit/Release(request_id, epoch, reason) ──▶  D 端释放/上交

三条协议规则，每条都由测试背书：

  • 幂等键 (request_id, epoch)：Ack 超时后 P 端保留所有权重发 Data（同 epoch）；D 端重复收到同 epoch 的 Data 只重发 Ack、不重复解码；epoch 过期（请求已释放或已换新 epoch）的消息被tombstone 拒绝且不污染当前状态——"释放后复用"攻击面：块被释放再分配给新请求后，旧消息到达必须无害；
  • 取消的三时机：交接前（P 直接回收）、Data 传输中（P 回收 + D 对无 Data 的 Prepare 超时清理）、Ack 后（D 端回收）——实验三用例全部"双侧登记清零、通道无残留"；
  • 统一回收路径：完成/取消/失败同一 release(reason)（第 4 章约定），重复释放报错。

正确性判据（验收原文）：同批请求在有无交接路径下输出逐 token 一致——实验固定种子 tiny、同 prompt、同长度，D 端续生成与单进程参考逐 token 相同（PASS）。

发现不一致时怎么办（验收原文"不以浮点误差放行"）：受控确定性基线（固定种子、贪心、同一输入序列）下，本实验把逐 token 全等设为判据——分叉时不允许以"浮点误差"直接放行：浮点扰动确实可能翻转近并列的 argmax，但归因需要证据。定位流程：先排除输入序列/缓存覆盖范围/位置与状态重建的不等（第 16 章开发期就有"历史双计数被误释为浮点差异"的实证）；再沿同一固定 token 前缀比较 logits——取分叉前最后一个位置，对照 P 端 prefill 末列 logits 与 D 端重建后重喂同一 token 的下一步预测 logits（注意两边比较的是消费了同一前缀之后的预测，一步偏移就会假不相等）；逐元素相等则查 D 端生成循环，不等则查 KV 重建（错位一层/一 token 都会在这里暴露）。若两侧 logits 只差浮点尾数且分叉处两候选近并列，才可记录为数值噪声并附证据。这套"先定位再修"的流程与第 2 章三层锚点对齐法同构。

11.4 合置 vs 分离的账 ​

分离的收益（干扰消除、按阶段选并行）要付的账：交接传输 + 两实例间负载失衡的排队。实验的传输扫描（gloo CPU 双进程，预热+交错重复）：

KV 长度 T交接字节传输耗时（相对）
168,328 B2.0 ms
3216,648 B4.3 ms
6433,288 B1.9 ms
12866,568 B4.8 ms

两个读数：小状态传输被固定延迟主导（字节翻 8 倍，耗时几乎不动，1.9–4.8 ms 波动）——真实场景同机 NVLink/跨机 IB 的延迟与带宽完全不同（未测），但"小消息吃延迟、大消息吃带宽"的结构（第 10 章 10.3）不变；带宽敏感性照此直线外推：T=40,960 的 Qwen3.5 请求状态 ≈503 MB（第 4 章账），在假设 50 GB/s 有效带宽下仅传输就要 ≈10 ms——这笔账必须小于分离省下的干扰时间，分离才赚。

所以选型判据是三条账的对比，而不是信仰：分离收益（干扰消除 × SLO 达标率）> 交接成本（状态字节 ÷ 有效带宽 + 排队）+ 实例配比失衡风险。短 prompt 高并发的聊天负载（状态小、干扰小）通常不值得拆；长文档负载（TTFT 押得重、状态大但带宽也需求大）是分离的主场（DistServe 的 goodput 提升即来自此类负载，S25）。带宽感知放置（prefill/decode 实例就近、跨机时状态走高带宽路径）是工程上的第一杠杆。

练习与答案 ​

练习 1：交接消息里 kv_len 声明了 1,000，但 token_ids 有 1,002 个。接收端应该怎么处理？答：校验约定 kv_len == len(token_ids) − 1 失败（1,000 ≠ 1,001），显式报错拒绝——绝不猜"多出的是不是还没入缓存的尾巴"。两端对"最后 token 是否已入缓存"的理解差一，输出会在 D 端首步静默分叉（11.2 约定 1 的反例化）。

练习 2：D 端收到 Ack 之后、Commit 之前，客户端取消了请求。谁负责回收？答：Ack 之后所有权已在 D——取消消息发给 D，D 走统一回收路径并回执；P 端此时已无该请求状态（收到 Ack 即清理），若取消消息误达 P，P 对未知 request_id 报错而不是静默吞掉。所有权协议的意义就是任何时刻恰好一方能对状态负责。

练习 3：同一 P 实例给两个 D 实例发交接，D1 的 Ack 在路上丢了。P 重发 Data 给 D1 的同时，新请求的 Prepare 到了 D2——会发生什么？答：不同 request_id 互不干扰（幂等键隔离）；D1 重收同 epoch Data → 幂等重发 Ack。若 P 等不到 Ack 决定放弃并 release，D1 稍后收到的旧 Data 命中 tombstone 被拒——迟到消息无害是协议的目标态。

练习 4：一条 Qwen3.5 T=8,000 的请求交接：KV 与循环状态各多少字节（fp32）？若只传 KV 会怎样？答：KV（fp32）= 24,576 B/token×8,000 ≈196.6 MB（bf16 则 98.3 MB）；循环状态固定 ≈20.7 MB（fp32；conv 1.8 + recurrent 18.9）。只传 KV：decode 端的 18 个线性层从零状态起步——输出立即且无报错地偏离正确答案（线性层的"记忆"丢了），这是比崩溃更危险的失败模式，判据必须逐 token 对照（11.3）。

练习 5：同机分离 vs 跨机分离，交接账有什么不同？答：同机（NVLink/主机内存）：带宽高（数百 GB/s 级）、延迟低——状态大也传得快，甚至可以零拷贝共享内存；跨机（IB/以太网）：带宽低一两个量级、延迟高——T=40,960 的 503 MB 在 50 GB/s 假设下要 10 ms，在 5 GB/s 下要 100 ms，直接吃掉分离收益。所以 DistServe 的"带宽感知放置"（S25）把 prefill/decode 实例的物理位置当作一等变量——分离的可行性由互联决定，不由算法决定。

小结：算了什么、慢在哪里、怎样验证 ​

  • 分离的账：收益=干扰消除+按阶段选并行（DistServe 的 goodput 口径，S25），成本=状态传输（字节÷带宽+固定延迟）+实例配比失衡——三条账对比后才知道拆不拆；
  • 交接对象=恢复推理的完整状态：Dense 是 KV（覆盖约定 kv_len=len−1、布局显式校验）；混合模型还有每请求固定 20.7 MB 的循环状态，只传 KV 会静默失忆；
  • 协议四阶段+幂等键+tombstone 把"恰好一方负责"变成可测试的性质：三时机取消、超时重试、释放后复用拒绝、重复释放报错——全部有断言；
  • 一致性判据：受控基线逐 token 全等；分叉沿固定序列比 logits 定位，不以浮点误差放行。
