第 15 章 · 生产部署与容量配置 ​

第 1 章我们用一条命令把 vLLM 跑了起来，但没有回答：这台机器该用什么配置、能扛多少流量、坏了怎么看见？ 本章把这些问题一次做完：逐项说明引擎配置（15.1）、以 vLLM 为主实现完成部署与观测（15.2）、画出容量曲线选可持续配置（15.3）、用实测账粗估并解释误差（15.4）。交付物是一个可启动、可压测、可观测的部署包与容量建议。

部署包在 experiments/exp_ch15_deploy/（serve.sh 启动 + bench_sweep.py 压测 + observe_metrics.py 观测 + capacity_curve.py 曲线 + mock_openai_server.py 本机自测 + README）。本机无 GPU、vLLM 未装（5.3）：脚本正确性在 mock 服务上实测签收，vLLM 上的全部数字标未测（部署包在有 GPU 的 Linux 上一键执行，复现条件在 README）。

15.1 回访第 1 章服务：配置逐项说明 ​

第 1 章的教学服务把一切藏在默认值里。生产引擎的启动参数每一项都对应前文一章的机制，逐项过一遍（S36 官方 CLI 文档）：

配置默认对应机制判断依据
--dtypeauto（权重精度）第 5 章精度bf16 是吞吐默认；fp32 只在质量边界排查时用；KV 另有 --kv-cache-dtype（fp8 系）——两件事分开决定
--max-model-len模型 config 派生第 4 章 KV 账上下文上限直接决定 KV 池形状：按真实负载的长度分布砍到够用（4096 的负载别开 32K）
--gpu-memory-utilization0.92第 4 章显存划分权重之外的预算全部给 KV/激活；留 8% 给碎片与突发——不是越大越好
--max-num-seqs版本相关（示例 256）第 9 章两本预算并发上限：批内请求数的护栏，防 KV 被打穿后的抢占风暴
--max-num-batched-tokens引擎定第 9 章分块 prefill每 iteration 的 token 预算——长 prefill 干扰 decode 时调小它（chunked prefill）
--tensor-parallel-size1第 10 章先算显存下限定最小 TP，剩下的卡给副本（10.4 次序）；TP 内部每层 2 次 all_reduce 是税
--enable-prefix-caching开第 4 章前缀复用多轮/共享系统提示的负载直接受益；哈希默认 sha256（S36）

两个部署判断先立住：max-model-len 是 KV 池的形状不是能力宣誓——按第 4 章公式，Qwen3.5-0.8B 每请求 T=8,000 约 98MB(KV)+10MB(循环状态, bf16)，上限开多大直接决定同时能装多少请求；并发与吞吐是两本账（第 9 章）——max-num-seqs 调大不等于容量变大，容量由 15.3 的曲线说了算。

请求面与第 1 章同构：OpenAI 兼容 /v1/chat/completions（messages、stream、max_tokens、超时与客户端取消按 OpenAI 语义）；模板由引擎按模型自动应用（S3）。架构支持核查先行：Qwen3.5 是 GDN 混合主干——启动前用包内 README 的核查命令确认所装 vLLM 版本支持该架构；不支持时按 6.4 不换锚、登记缺项（所需版本），Qwen3-0.6B 只用于脚本链路自测，不替代部署验收。

观测面（S35）分两层：服务级——/metrics 暴露 Prometheus 指标：vllm:num_requests_running/waiting（调度队列）、vllm:kv_cache_usage_perc（KV 池水位）、vllm:prompt_tokens_cached_total ÷ prompt_tokens_total（前缀命中率，第 4 章机制的直接读数）；请求级——TTFT/TPOT/排队/prefill 时长直方图（正是 3.3 的指标定义）。两处 TTFT 口径有差，对表先说口径：/metrics 是服务端阶段和（queue+prefill，不含网络）；bench_sweep.py 是客户端口径——从请求实际发出计到首个内容帧到达，含网络往返与服务端排队，不含客户端并发信号量的等待（client_wait_s 单列，用于发压不足检测，S34/S35）。observe_metrics.py 周期抓取转 CSV，容量实验与线上看同一份数据。日志与 metrics 的关系：默认日志为聚合粒度（逐 iteration 统计是单独开关、默认关，需排障时再开）、metrics 按直方图/计数器聚合——排障先 metrics 定方向、再日志定 iteration、最后 trace 定算子（3.5 的三层对齐）。

15.3 容量曲线：到达率扫描与可持续配置 ​

容量问题（9.4）在部署语境的完整做法：

  1. 定 SLO（先于测量，3.3 口径）：例 ttft_p99_ms<=2000, tpot_p99_ms<=200——分位数样本单位写清（TTFT/TPOT 按请求、ITL 按 token）；
  2. 定负载分布：输入长度分布 × 输出长度分布 × 到达率——bench_sweep.py --rates 1,2,4,8 … 每档按目标到达轨迹发压，记录目标到达与实际发出两列（发压不足检测）、并发上限、排空时长；
  3. 算 goodput：同时满足全部 SLO 的请求占比 × 吞吐——这正是 DistServe 的 goodput 口径（S25；vLLM bench 也内置 --goodput，S34）；
  4. 画曲线读点：capacity_curve.py 产出 capacity.csv/md/svg——吞吐与 goodput 随到达率爬升、p99 延迟在某档破线，SLO 内最大到达率即可持续点，运行点取其 70–80% 留突发与长尾余量。

曲线之外的两个判定纪律（9.4 原样适用）：等待深度持续增长而不是波动 = 真饱和；停压后排空时长随负载增长 = 稳定过载而非崩溃。失败/取消请求全部入账——goodput 的分母包含它们。

15.4 粗估与误差：先算账，再用实测校准 ​

纯测量之前先做粗估（手算在测量之前，第 3 章纪律）。以部署包默认锚（Qwen3.5-0.8B、24GB 卡、bf16）为例，全部数字来自第 4 章的账（S0/S4）：权重 0.8B×2B≈1.6GB；gpu-memory-utilization 0.92 给出 22.1GB 预算，扣除权重与激活预留约 2–3GB，KV+循环状态预算 ≈17–18GB；每请求状态 = 12,288B/token×T（全注意力层）+ 约 10.4MB 循环状态（bf16）。取 T=8,000：每请求 ≈98MB+10.4MB≈108MB → 同时驻留约 160 条满上下文请求——这就是 max-model-len 与 max-num-seqs 联动的算术。吞吐侧的粗估用 decode 带宽下界（第 3 章 Roofline：每 token 读全部权重 1.6GB ÷ 显存带宽）——只能给量级，必须实测校准。

粗估的误差来源，部署后逐项对表（15.4 验收）：调度开销与 batch 组成（第 9 章）、内核效率与算子覆盖（第 6/8 章）、前缀命中率波动（第 4 章——命中率 30% 与 70% 的 TTFT 完全不同）、以及模型行为本身（输出长度分布偏离假设时容量随之移动）。方法结论：粗估定数量级与资源下限，曲线定运行点，metrics 做在线复核——三层各司其职，谁也不冒充谁。（回填校准须部署环境的实测带宽/阶段时间与 /metrics 数据——本机未测，方法与对照表已备：config/capacity-template.md 第 5 节。）

练习与答案 ​

练习 1：8GB 卡部署 Qwen3.5-0.8B（bf16），--max-model-len 4096，粗估 KV 池能装多少条 T=4,096 的请求。答：预算 0.92×8=7.36GB − 权重 1.6GB − 激活预留 ≈1GB → ≈4.7GB；每请求 12,288B×4,096≈50MB + 循环状态 10.4MB ≈ 60MB → ≈78 条。把 max-len 砍到 2K：每请求降到 ≈35.5MB（KV 减半但固定循环状态 10.4MB 不缩）→ ≈134 条，约 1.7 倍而非翻倍——固定状态稀释收益，这就是"按负载分布定上限"的算术。

练习 2：压测发现 8 req/s 档 max_wait 持续增长但吞吐不涨，而 4 req/s 一切正常。先查什么？答：先确认瓶颈在服务端还是客户端——对照目标到达与实际发出（发压不足时"容量"是客户端上限，9.4）；若确实服务端饱和（等待持续增长、排空变长），看 metrics 的 kv_cache_usage_perc 是否顶格：顶格是容量约束（调 max-num-seqs/max-model-len 或加卡），不顶格而 running 低则是计算或调度约束（TP/batch 旋钮）。先定位资源类别，再动配置。

练习 3：goodput 与吞吐什么关系？什么时候差距最大？答：goodput = SLO 达标请求占比 × 吞吐——分母包含失败/超时。过载区差距最大：吞吐在饱和后仍缓慢爬升（排队换批量），但 p99 破线让达标率骤降，goodput 反而下降——容量曲线的"拐点"在 goodput 而不在吞吐，这正是 S25 把 goodput 作为优化目标的原因。

练习 4：--max-num-batched-tokens 从 8192 降到 2048，预期什么变化？答：每 iteration 的 token 预算减至 1/4（8192→2048）——长 prefill 被切得更碎，decode 步更均匀、短请求 TPOT 尾延迟改善（第 9 章分块取舍），代价是 prefill 吞吐下降、TTFT 变差。押 TTFT 的服务别动它；押 TPOT 且长 prompt 占比高的服务可以调小——同一参数没有无条件正确值。

练习 5：为什么部署包坚持"先架构核查再启动"？答：Qwen3.5 是 GDN 混合主干，引擎对其（尤其循环状态的处理）支持随版本变化——config 字段存在不等于已支持（第四节边界原文）。核查先行避免把"引擎悄悄回退/报错"误当性能问题；不支持时登记缺项与所需版本，锚定不换（6.4），对照模型只做链路自测。

练习 6：粗估给出 78 条容量，实测曲线显示 55 条就破 SLO。列出至少三个候选误差来源与验证方法。答：(a) 激活与运行时预留被低估——看 metrics 的显存划分与 kv_cache_usage_perc 顶格时刻的并发数；(b) 输出长度分布比假设长——decode 占比高时 TPOT 尾延迟先破线，核对压测的 output_len 分布；(c) 前缀命中率低于假设/调度开销——看 prompt_tokens_cached_total 占比与 iteration 日志的批组成。每个来源都能在 metrics/日志里找到对应读数——误差不是丢脸的事，不解释的误差才是。

小结：算了什么、慢在哪里、怎样验证 ​

  • 配置逐项对回机制：dtype/精度、max-model-len/KV 账、内存预算划分、两本预算与分块、TP 按显存下限、前缀缓存命中率可观测——第 4/5/9/10 章在启动参数上的落点；
  • 部署三件套：serve（参数化启动+架构核查）、bench（到达轨迹+四列记录+goodput）、observe（服务级 gauge+请求级直方图）——本机 mock 签收逻辑，GPU 环境一键复现（未测如实标注）；
  • 容量 = 曲线不是数字：SLO 先行、goodput 口径（S25/S34）、SLO 内最大到达率取 70–80% 做运行点；等待深度与排空判定饱和（9.4）；
  • 粗估（第 4 章账+Roofline）定量级与下限，实测曲线定点，metrics 在线复核——三层各有误差边界，逐项对表。
