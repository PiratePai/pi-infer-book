第 1 章 · 跑通模型：从输入到输出 ​

一句话进入，一段话出来——中间发生了什么？本章把这条链路完整走一遍：你发出的一段文字，如何变成 token、经过模型、逐个字流回来。走通之后，你能指出首 token、后续每个 token 和结束事件分别发生在哪，遇到启动失败和输入报错时知道先看哪里。

本书配套一个教学用最小服务（experiments/exp_ch1_serving/serve_pi.py，本地加载 Qwen3-0.6B，约一百行标准库代码）和一个生产引擎（vLLM）两条路径。前者每行都可读，后者是业界日常使用的入口——两条路径的请求格式几乎一致，这正是本书的方法：先用小而透明的实现看清机制，再迁移到生产工具。

1.1 权重、tokenizer、chat template：三个各司其职的部件 ​

从磁盘上一个模型目录（本机 models/qwen3-0.6b/，revision 见 versions.md）说起，里面真正参与一次请求的是三个部件：

① 模型权重（model.safetensors，约 1.4GB）。一堆浮点数，按 config.json 描述的结构摆放：28 层、hidden 1024、16 个 Q 头 / 8 个 KV 头、词表 151936（config 直查，references S1）。第 2 章会把每层拆开写出来；本章只需知道：权重在服务启动时加载一次，之后常驻内存，每个请求共用，不会因请求而改变。

② tokenizer（tokenizer.json + vocab.json）。文字与整数（token id）的双向映射。模型不认识文字，只认识 id：

python
from transformers import AutoTokenizer
tok = AutoTokenizer.from_pretrained("models/qwen3-0.6b")
ids = tok("你好，推理加速", add_special_tokens=False)["input_ids"]
# [108386, 111224, 872, 103059, 113552, 99432] —— 六个 token
tok.convert_ids_to_tokens(ids)  # ['你好', '，', '推理', '加速', ...]

同一句话的切分是确定的（无随机性）；"推理加速"被切成"推理"+"加速"而非单字——切分粒度决定了输入长度，输入长度又决定后面每一步的成本，这条因果链第 3 章会量化。

③ chat template。原始模型只延续文本，"对话格式"由模板给出：把 {"role": "user", "content": "你好"} 这样的结构化消息包装成带特殊标记的 token 序列：

python
tok.apply_chat_template(
    [{"role": "user", "content": "用一句话解释什么是 KV 缓存。"}],
    add_generation_prompt=True, tokenize=True)["input_ids"]
# [248045?, ...]  实际形如 <|im_start|>user\n…<|im_end|>\n<|im_start|>assistant\n
1
2
3
4

模板属于模型发布的一部分（写在 tokenizer 配置里），换模型就要换模板——草稿模型与目标模型模板不一致，是后面投机解码实验里真实的错配事故来源（第 7 章 7.5 检查清单第 2 条）。

三者分工小结：tokenizer 与 template 在"文字 → token id"这一步各出现一次；权重常驻；请求的其他一切发生在 token id 之上。

1.2 从 logits 到下一个 token：贪心、采样与停止 ​

token id 序列进入模型，出来的是 logits——对词表每个候选 token 的打分（Qwen3-0.6B：每步 151936 维）。从打分到"下一个 token 用哪个"，有两条路：

  • 贪心（greedy）：永远取 argmax。确定性——同样输入永远同样输出。本书所有对照实验的基线口径（复现友好）。
  • 采样（sampling）：按 softmax(logits/T) 概率抽取，temperature、top-k 控制分布形状。多样，但引入随机性——对照实验须固定 seed 才可复现（第 7 章 SamplingSpec 把这套口径显式化）。

选出一个 token 后并不结束：它被拼回输入，再算下一个 logits——这就是"自回归生成"。什么时候停？三个条件任一满足：

  1. EOS：模型输出结束标记（如 <|im_end|>）。注意检查的是新生成的 token——prompt 里出现结束标记不触发停止（第 2 章解码循环同一约定）；
  2. 长度上限（max_tokens）：客户端设的护栏，防止模型"停不下来"烧钱烧时间；
  3. （服务端还有请求超时/取消，第 15 章展开）。

一个真实的观察（本章实验 E1，Qwen3-0.6B 默认开启思考模式）：请求"用一句话解释 KV 缓存"，返回的 32 个 token 以 <think>\n嗯，用户问的是… 开头——"一句话"的期望输不出现在开头，模型先在思考段里自言自语。这不是 bug：思考段也是正常生成的 token，同样受上面三条停止条件约束；要改变行为得在模板层处理（enable_thinking=False，练习 4 动手改）。这件事的教学价值在于："输出长度"是模型行为、模板设置与停止条件三者共同决定的，不是单一旋钮。

1.3 请求的一生：预处理 → prefill → decode → 流式 ​

把一条请求放进时间线（本章实验 E2 的实测事件，客户端相对毫秒）：

text
t=0        收到请求（received）：HTTP 解析、参数校验
t≈162      first_token：预处理 + prefill 完成，第 1 个 token 到达
t≈162…1859 token×31：decode 逐步产出，每 token 平均 ≈55ms
t≈1859     done：命中 max_tokens=32，结束
1
2
3
4

四个阶段，"只做一次"的边界各不相同：

阶段做什么次数
预处理chat template → tokenize → id 序列每请求一次
prefill整段 prompt 一次前向：算出每个位置的 KV 与首个 logits每请求一次
decode每 step 只喂上一个新 token，历史 KV 复用（第 2 章实现，第 4 章管理）每 token 一次
流式输出每算出一个 token 立即推送（SSE），不等全部生成完与 decode 同步

两个结构性的观察，全书反复用到：

  1. 首 token 时间（TTFT）天然不等同于后续每 token 时间（TPOT）：本例 162ms vs ≈55ms——prefill 是一次性整段计算，decode 是逐 token 增量。负载里 prompt 越长，两者差距越大（第 3 章 3.3 把它们定义为正式指标）。
  2. 流式不减少任何计算，只改变"何时把已有的 token 给你"。它降低的是感知延迟（本次请求在 0.16s 收到第一个 token，1.86s 收到完整结果）。

留意两个连续的 token 事件。生成「 缓」时，ID 84238 所在事件的文本为空，到 ID 241 才输出完整的「 缓」。两个 ID 都计入生成长度和时间统计。增量解码器保留暂时拼不成字符的字节，客户端只需按顺序拼接各事件的 text。

读请求日志：experiments/exp_ch1_serving/request_log.jsonl 每事件一行（request_id / event / t_ms / …）。验收要求的三类事件在日志里各对应：first_token（含 prefill）、token（后续）、done（结束，带 stop_reason）。

错误定位（实验 E3 实测；思路：先看客户端拿到什么状态码，再对照服务端日志有没有 received 事件）：

症状HTTP服务端表现定位
{"not-json{" 非法 JSON400 bad_request日志无 received（参数校验在生成前）客户端请求体格式
多了 "temperature":0.7400 unknown_param无 received查服务接口文档（本服务只收 prompt/max_tokens/stream）
3000 字 prompt413 prompt_too_long无 received超过 2000 字符上限（教学服务的护栏）

一个通用顺序：客户端状态码 → 服务日志有无 received → 有 received 则看 token 事件停在哪。四种错误都发生在"进模型之前"，所以日志里连 received 都没有——这就是"参数校验前置"的设计：坏请求不消耗宝贵的生成资源。

练习与答案 ​

练习 1：用 apply_chat_template 分别取 add_generation_prompt=True 与 False 的 token 序列，diff 两者结尾。答案：True 版本结尾多出 assistant 段的启动标记（形如 <|im_start|>assistant\n 对应的 id）——这就是"让模型接着说话"的交接棒；生成期间模型的所有输出都接在这之后。

练习 2：从 E2 的事件流（raw.json）手算 TTFT 与平均 TPOT，并解释为什么两者不相等。答案：TTFT=first_token 时间 162ms（含 HTTP、预处理、prefill）；TPOT=(最后一个 token 1858.8−首 token 162.2)/31≈54.7ms/token（纯 decode 增量步）。不相等的原因：prefill 是一次性整段前向，decode 每步只算一个新 token——成本结构不同（第 3 章 3.3 起作为正式指标）。

练习 3：客户端报告"请求似乎超时了"，服务日志里却有完整的 received → first_token → … → done 记录。最可能的故障层在哪？答案：在服务之后、客户端之前——响应已生成并写出（done 都记了），问题在传输/代理缓冲/客户端读取（例如用了不带 -N 的 curl：SSE 被缓冲，全部生成完才一次性显示，看起来像卡死）。日志完备时"先对齐两端时间线"能直接排除模型层。

练习 4：把请求模板改为 enable_thinking=False（apply_chat_template 的参数）重发同一 prompt，观察输出差异。答案：输出不再以 <think> 段开头，直接给答案正文；同样 max_tokens 下有效答案更早出现。模板参数改变的是"模型从什么状态开始接着说"，不改变模型本身——这是 1.1"模板属于模型发布的一部分"的动手印证。

练习 5：max_tokens=32 时模型经常"话说一半"就停。这是 bug 吗？答案：不是——是停止条件 2（长度护栏）触发，done 事件的 stop_reason=max_tokens 明说了一切；把 max_tokens 调大或让模型自然输出 EOS（stop_reason=eos）才拿到完整回答。判断依据永远是日志里的 stop_reason，不是输出文本的观感。

小结：算了什么、慢在哪里、怎样验证 ​

  • 一条请求 = 预处理（一次）+ prefill（一次）+ decode（每 token 一次）+ 流式推送（与 decode 同步）；权重与模板常驻、逐请求复用的是"结构"，不是"状态"；
  • TTFT 与 TPOT 成本结构不同（162ms vs ≈55ms 实测），流式降低感知延迟不减少计算——这两个事实是第 3 章指标体系与第 9 章调度的起点；
  • 验证改动的方法：固定输入 + greedy 确定性 → 输出可逐 token 对照；逐事件请求日志 → 任何"慢/停/错"都能定位到阶段；错误请求在参数校验层被拒绝（日志无 received）→ 坏输入不消耗生成资源。
