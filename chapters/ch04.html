第 4 章 · KV Cache：从复用到内存管理 ​

第 2 章的解码循环每步只喂一个新 token——前提是历史 token 的 K/V 已经算过并留着。本章的问题：这些留着的 KV 占多少内存、谁来分配、谁能共享、出错怎么回收？ 这是推理引擎内存管理的主战场：KV 随上下文线性增长、随请求并发叠加，管不好就是碎片与泄漏。

配套实现 pi_infer/kv.py（块分配器、块表、前缀树、分页缓存），实验 experiments/exp_ch4_kv_cache/。

4.1 从"每步重算"到"只算新的" ​

第 2 章实验 3（增量=全量）已经证明：把输入切成任意段增量前向，logits 逐位一致。原因是因果注意力下，位置 t 的 Q 只与 0..t 的 K/V 相乘——历史 K/V 一旦算出，后续每步都复用同一个值（RoPE 只依赖绝对位置，第 2 章性质 1 的用武之地）。

于是生成从"每步 O(T) 全量重算"变成"每步 1 个 token"：FLOPs 从 2P⋅T 降到 2P，代价是必须存下 K 和 V——空间换时间的典型交易。存的量（第 3 章的账）：

KVBytes(T)=2×nlayer×T×hkv×dh×b

tiny（fp32、GQA hkv=2）每 token 512 B；MHA 则翻倍——GQA 的红利在这里兑现。低秩压缩状态（MLA 一类）能再压小，机制不同：存的是压缩表示、注意力时再解压——本书只用一个短框说明其存在，不展开（v1.7 目录 4.2）。

4.2 混合模型另列账：KV 与循环状态是两种东西 ​

上面那笔账只对全注意力模型成立。Qwen3.5-0.8B 的 text 主干是 GDN 3:1 混合：24 层里 6 层全注意力（存 KV），18 层线性注意力（存循环状态）。两类状态的成本结构完全不同（config 与实现直查，references S0/S4）：

状态形状（实测）增长方式fp16/fp32 每请求成本
全注意力 KV[B,2,T,256] /层 × 6 层随 T 线性2×2×256×6×T×2B=12,288B/token
GDN conv state[B,6144,4] /层 × 18 层固定6144×4×18×4B≈1.8MB
GDN recurrent state[B,16,128,128] /层 × 18 层固定16×128×128×18×4B≈18.9MB（fp32）

两个直接推论：

  1. 容量公式变成两段：总状态 ≈12,288B×T+20.7MB。短上下文时固定状态占主导（T=1,000 时 KV 仅 12MB，不敌 20.7MB）；长上下文时 KV 反超（T=40,960 时 KV ≈ 503MB）。"混合模型省显存"是有条件的结论，条件就是这段账。
  2. 恢复与所有权规则不同：KV 可以截断到任意前缀再继续（重算尾部即可）；循环状态是逐步演化的——要"回到过去"只能保存快照或从头重放，没有"截断"这个操作。这直接影响：投机解码的拒绝回滚（第 7 章）、P/D 分离的交接对象（第 11 章——只传 KV 覆盖不了混合模型，循环状态必须一并交接）。本书第 7 章 MTP 实验选全量重算路径，正是绕开循环状态回滚的教学取舍。

4.3 为什么分页：连续缓存的三宗罪 ​

第 2 章的 SimpleKVCache 把 KV 存成连续张量、每次 append 拼接整段。三个致命问题：

  1. 预留下限：不知道请求会生成多长，就得按 max_seq_len 预留——1 条长上下文请求预留 GB 级，用不满就浪费；
  2. 碎片：请求结束释放的连续大块，与新请求的尺寸对不上；
  3. 无法共享：两条请求前缀相同，连续布局下各自的缓存各存一份。

解法与操作系统虚拟内存同构：固定大小的块（block）+ 每请求一张块表（block table）把逻辑位置映射到物理块。这就是 pi_infer/kv.py 的三个部件：

text
BlockAllocator   固定块池：allocate(n) / free(ids)，物理块布局 [块, K/V, 层, Hkv, 槽位, D]
BlockTable       每请求：逻辑块序号 → 物理块 id，valid_tokens 记录尾块有效槽位
PrefixCache      前缀树：键 (model_id, token 块)，整块精确匹配，块引用计数

尾块细节：prompt 长度未必是块大小整数倍，最后一块只有部分槽位有效（valid_tokens）；部分匹配的尾块不共享——它还没写满，别人接着写会污染（4.5 写时复制）。

4.4 前缀复用：块共享与引用计数 ​

很多请求共享同一前缀（系统提示、few-shot 模板、多轮对话历史）。前缀树按块粒度登记"哪些 token 序列住在哪些物理块"，新请求 request(model_id, prompt) 时：

text
match → 命中 k 个整块 → 直接引用这些物理块（ref_count + 1）
      → prefill 只算未命中的尾段（从 num_matched 起）

2

实验 E2 的时间线（实测输出）把引用计数走了一遍：

B 命中 A 的前缀: num_matched=4（尾块部分命中不计入 → 不共享）
A 释放后: 2 → 1 块（共享块被 B 引用，不归还）
B 取消释放后: → 0 块（引用归零，才真正归还块池）
C 失败释放后: 块池恢复 32/32（failed 与 finished/cancelled 同一回收路径）
重复释放: DoubleFreeError ✓

三条工程规则都在里面：引用计数保护共享块（A 先走不拆 B 的台）；释放原因不影响回收路径（完成/取消/失败统一 release(reason)——第 11 章交接的失败路径沿用此约定）；重复释放必须报错（静默的话，块被二次归还 → 两个请求拿到同一块 → 数据互相覆盖，这是最难查的一类串状态事故）。

命名空间：缓存键含 model_id——两个模型同 token 序列的 KV 完全不同，跨模型命中就是数据污染，测试有专项用例。

一个实验中实际撞见的现象值得记录：在同一块池里重复用相同 prompt 发起请求，第二次会命中第一次已释放请求登记的完整前缀——释放后块归还池子，但前缀树保留"弱索引"，只要那些块没被重新分配覆盖，仍可重新领用（pi_infer 用块版本号验证有效性）。这正是"热缓存"的语义：刚释放的 KV 短时间内还救得回来。

4.5 尾块与写时复制 ​

共享块是只读的。若 B 命中 A 的尾块（部分槽位有效）并继续写满它，A 的 KV 就被改写。两个可选纪律：

  • 整块才共享（pi_infer 的选择）：部分命中的尾块一律重算，简单、无污染，代价是至多一个块的重算；
  • 写时复制：命中尾块真要写时先复制一份。truncate_to（第 7 章回滚用）内部就是这么做的：回滚位置落在共享块中间时，先 allocate 一块新的、复制内容、替换块表项——别人的完整前缀不受影响。

真实配置账（6.4）：把 4.2 的两段式公式代进 Qwen3.5-0.8B——1 条 T=40,960 请求的状态 ≈ 503MB(KV) + 20.7MB(循环)；24GB 显卡理论上限约 46 条这样的满上下文请求（只算状态，未扣权重与激活）；同卡若服务 T=1,000 的短请求，状态仅 32.7MB/条但其中 63% 是固定循环状态——短请求并发下循环状态成为刚性占用。这是账本推演（非实测容量），实测在 15 章部署环境完成。

降级声明（5.3）：E1–E3 为正确性/行为验收（CPU 签收）；E4 为同机相对对照，不构成性能结论。真实规模的容量账为公式推演，部署实测标"未测"。

练习与答案 ​

练习 1：Qwen3-0.6B（28 层、8 个 KV 头、head_dim 128）fp16 部署，单请求 T=8,192 的 KV 是多少？答：2×28×8,192×8×128×2B=939,524,096B≈940MB。40 条并发满上下文请求 ≈ 37.6GB——单卡放不下，这就是为什么长上下文服务必须做块池上限与抢占（4.3/第 9 章）。

练习 2：块大小 16、块池 1,000 块。请求 A（prompt 35 token）与 B（prompt 33 token，前 32 token 与 A 相同）先后到达。A、B 各持有几块？块池剩几块？答：A：⌈35/16⌉=3 块；B 命中 A 的 2 个整块（32 token）+ 自身尾块 1 token → 新分配 1 块。B 实际持有 3 块但只新占 1 块；池剩 1000−3−1=996 块（共享块只算一次）。若 B 是独立请求不共享：剩 994——前缀复用在多轮对话场景的节省就是这个差乘以会话数。

练习 3：若把 4.4 的"整块才共享"放宽为"尾块也共享"，最快的翻车方式是什么？答：B 命中 A 的尾块（如 4/16 槽有效）继续写入——B 的第 5..16 槽写进 A 也在读的物理块。A 后续 decode 读到 B 的 KV，输出在某个 token 后悄悄分叉，且无任何报错。这正是 4.5 写时复制要防的事故，也是"正确性判据必须逐 token 对照"（E1）的动机。

练习 4：release(reason="cancelled") 与 "failed" 为什么要走同一回收路径？若 failed 走"泄漏不回收"会怎样？答：失败请求同样持有块引用；不回收则引用计数永不归零，共享块永不出池——一次模型报错之后容量永久缩水（泄漏）。统一路径保证任何结束原因都归还"它独占的块"，共享块等最后一个引用者释放。

练习 5：GDN 混合模型做投机解码，拒绝回滚 5 个 token：全注意力层与线性注意力层分别需要什么操作？答：全注意力层 truncate_to(len−5) 即可（KV 支持任意前缀截断后重算）；线性注意力层的循环状态没有"截断"语义——要么在起草前保存状态快照（回滚=恢复快照），要么全量重放重算（第 7 章 MTP 实验的选择）。混合主干实跑"须验证循环状态恢复"（第 7 章验收原文）指的就是这一条。

练习 6：E4 里复用 24 token 只省了零点几毫秒。给出一个"复用收益显著"的负载画像。答：prefill 占比大的负载——例如共享 4K 系统 prompt 的 50 并发多轮对话（每次命中 4K/16=256 块，省掉 4K token 的整段前向），或长文档问答服务。反之纯短 prompt 单轮聊天几乎无收益。判据：收益 ≈ 命中 token 数 × 每 token prefill 成本。

小结：算了什么、怎么管、怎样验证 ​

  • KV 每 token 字节 = 2nlayerhkvdhb，GQA 减半；混合模型是"随长度线性 + 每请求固定"两段账，循环状态的恢复语义（快照/重放，无截断）决定回滚与交接的实现方式；
  • 分页三件套（块池/块表/前缀树）解决预留、碎片、共享三个问题；尾块部分匹配不共享，写时复制保护共享块；
  • 正确性判据是四组合逐 token 一致；工程判据是取消/失败统一回收、重复释放报错；容量判据是理论字节=张量字节；
  • 复用收益只作用于 prefill 段，收益大小 = 省下的计算 × prefill 占比。
