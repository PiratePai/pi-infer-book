第 10 章 · 多卡推理与通信基础 ​

单卡装不下的大模型，或单卡喂不饱的吞吐，都要走向多卡。本章的问题是：把一份计算拆到多张卡上（或复制成多份），各自省什么、额外传什么？这笔通信账怎么算、怎么验？

三种基本拆法（10.1），支撑它们的通信原语（10.2），拆分位置与同步点（10.3），最后按显存/吞吐/SLO 对照选型（10.4）。配套实现 pi_infer/comm.py（进程级小张量验证 + 字节记录），实验 experiments/exp_ch10_comm/。本机无 NVIDIA GPU、无 NCCL：全部验证走 gloo CPU 进程——正确性与字节账签收，设备性能标"未测"（5.3）。

10.1 三种拆法：TP、PP 与服务 DP ​

从两个不同的"装不下"出发。模型装不下：一张卡放不下全部权重——把模型切开：沿层的宽度切（每张卡持每层的一部分矩阵），是张量并行（TP）；沿深度切（每张卡持连续几层），是流水线并行（PP）。吞吐不够：模型装得下但请求处理不过来——复制多份完整模型各自服务，入口分发请求，是服务级数据并行（下称 DP 副本；推理时各副本独立算，没有训练里的梯度同步——本章不讲训练并行）。

拆法省什么额外传什么额外同步
TP每卡显存 ÷P（权重按行切）每层 2 次输出聚合（all_reduce）每卡每步都到场
PP每卡显存 ÷P（按层切）阶段边界 1 次激活传递（p2p）阶段间接力（有 bubble）
DP 副本吞吐 ×P（模型不变）入口路由（不传张量）无（各副本独立）

KV cache 也随切分位置走（第 4 章那笔账在多卡上的延续，口径推演、多卡未测 5.3）：TP 切的是注意力头，MHA/GQA 下每卡 KV = 整组 ÷ TP（KV 头跟着 Q 头切到各卡）；KV 头数少于 TP 数时按卡复制——GQA hkv=2 的模型从 TP=4 起每卡重复保存 KV 头，省显存的红利被复制吃掉一截；MLA 类单 latent 头结构切不动、每卡各存一份压缩 KV（vLLM 的 get_num_kv_heads 即此口径：按 TP 均分、除不尽则复制，S37；DeepSeek 生产部署因此改用注意力数据并行，S17）。PP 沿层切，每卡只存自己阶段的 KV——第 11 章 P/D 交接"按阶段持状态"的视角与此同源。

最小可验证版本（实验实测）：TP2 把一个 Linear(16→16) 按输出维切成两个 16→8，各 rank 算各自半块的 XWi⊤，一次 all_reduce 求和后与单进程完整 Linear allclose（max|Δ|=0）——列切分+求和聚合的正确性一目了然。PP2 把 tiny 模型（恰好 2 层）按层拆开：rank0 算 embedding+layer0 得 hidden，p2p 发给 rank1 算 layer1+norm+lm_head，与单进程完整前向 allclose（0 误差）。两个组合分别对应上表中间两行的最小实例。

10.2 通信原语：数据流、结果与字节数 ​

多卡原语一共就几个，把"谁发多少字节"算清，第 11/12 章的交接与专家通信都是它们的组合。设 P 个 rank、每 rank 持有 N 元素 fp32 张量（下表为逻辑载荷口径：应用层交给通信库的张量字节；ring 等算法在链路上实际收发的更多，见后）：

原语数据流结果逻辑载荷（每 rank 发送）
send/recv点对点一 rank 收到另一 rank 的张量N×4 B（发送方）
broadcastsrc → 全部所有 rank 拿到 src 的数据N×4 B（仅 src）
all_reduce全互交换+归约所有 rank 拿到逐元素和N×4 B（各自输入）
reduce_scatter归约后切片rank i 拿到输出的第 i 块（N/P）N×4 B（输入）
all_gather拼接所有 rank 拿到全拼接结果（P×N）N×4 B（各自块）

进程级验证（实验，world=2/4，[16] fp32 小张量）：五原语逐一执行，各 rank 与单进程手算参考 allclose——全部 0 误差通过；非整除 shape、rank 间参数不一致等非法输入显式报错（shape_checks 全过）；进程退出无残留。这套"分布式执行 vs 单进程参考"的对照，就是并行正确性的"逐 token 一致"——机制换掉，判据思想不变。

字节账的双算（验收要求 ZCode 与评审独立手算、与 ByteLog 对表）：comm.py 的 ByteLog 记录每次通信的应用层载荷。以 world=4、[8] fp32 为例：p2p 每 rank 32 B、broadcast 仅 src 32 B、all_reduce 每 rank 32 B（Σ=128 B）、reduce_scatter 输入 32 B/每 rank、all_gather 输入 8 B/每 rank——42 组字节记录与手算全部一致。另一口径也要会算：ring all_reduce 链路上每 rank 实际收发约 2P−1P⋅N⋅4 B（算法内部分块走 P−1 圈）——逻辑载荷 ≠ 链路传输总量，报通信量时先说口径。TP2/PP2 的账也随之落定：TP2 的 all_reduce 聚合 [32] fp32=128 B（逻辑载荷）；PP2 的 hidden 传递 [256] fp32=1,024 B——乘上真实模型的 B·T·d 就是生产量级。

10.3 切分位置 ↔ 通信与同步点 ​

把 TP 放进一个 block（10.1 的 Linear 推广到注意力与 FFN）：TP 在每个 block 的注意力输出和 FFN 输出各插一次 all_reduce——通信点跟着切分位置走，每个都要全 rank 同步。PP 的通信点在阶段边界（一次 p2p），但同步代价换成了流水线气泡：前一阶段的最后一批没到，后一阶段只能等。

三个因素决定这些点有多贵（实验小张量数据，gloo CPU、同机相对）：

  1. 固定延迟主导小消息：[8] 与 [1024] fp32 的 all_reduce 都在毫秒级（0.8–2.9 ms 量级，world=2→4 明显上升）——小张量通信的成本主要是"组织通信"而不是搬运字节；
  2. 带宽主导大消息：字节数大到带宽项 bytes/β 超过延迟项后，成本随字节线性——所以真实 TP 通信按 B·T·d 计，batch 越大单字节摊的延迟越薄；
  3. batch 摊薄：一次 all_reduce 服务整批 token，B⋅T 越大，每 token 通信成本越低——这与第 9 章"batch 摊薄权重搬运"是同一个杠杆的通信面。

生产里 TP 的 all_reduce 走 NVLink/IB（未测），工程量级：通信暴露时间 = 字节数 ÷ 有效带宽 + 固定延迟，能否与计算重叠取决于实现——至少解释一处通信暴露时间（验收条款）的账：PP2 的边界 p2p（1,024 B）在 rank1 等待期间完全暴露；TP2 的 all_reduce 在两 rank 半块计算完成后串行执行、全程暴露——消除暴露的办法是切小通信块与计算重叠（如把 B·T 分片逐片聚合），本书不实现，账先立起来。

10.4 同样卡数：模型并行还是副本服务？ ​

8 卡预算的两个花法：TP=8 跑一个 8 卡才装得下的模型 vs 8 个副本各自跑单卡模型。账本对照（不实测，按机制推演）：

维度TP=8 单实例DP=8 副本
单卡显存权重 ÷8（能装大模型）全量权重（模型必须单卡装得下）
单请求延迟每层 2 次 all_reduce 串进关键路径，通信吃掉部分并行收益无额外通信，与单卡相同
吞吐受通信与同步限制，通常 < 线性≈ 线性 ×8（入口分发不传张量）
故障域一卡故障全实例停一副本故障只降容量 1/8
尾延迟大 batch 通信突发会顶 TPOT p99副本间独立，尾延迟由各自调度决定

结论是条件性的：装不下 → 只有模型并行一条路；装得下且要吞吐/SLO → 副本服务通常更划算；混合形态（TP 小组 + 组间 DP 副本）是生产常态——先用 10.1–10.3 的账算每种的通信/显存/延迟，再按 SLO（第 9 章口径）选。第 11 章的 P/D 分离会给出第三种"按阶段拆实例"的花法，第 12 章的专家并行（EP）则是 TP 思想在 MoE 上的变体。

降级声明（5.3）：gloo CPU 进程验证与字节账签收；NCCL/NVLink/IB 行为、真实多卡吞吐与气泡占比、TP/PP/DP 的设备端性能对照——全部未测（无多卡）。DP 副本未做多进程实跑（无多卡），对照为机制推演 + 第 9 章调度器的多实例口径。

验收对照基准条款：先用进程和小张量验证正确性（五原语 allclose 0 误差、TP2/PP2 vs 单进程参考一致）；字节账与手算双算一致（42 组，逻辑载荷口径 + ring 公式另列）；解释通信暴露时间（10.3 PP2 边界/TP2 聚合两处）；"完成可用的双卡配置"按 5.3 降级——无多卡，字节账与进程验证交付，设备性能项标未测。

练习与答案 ​

练习 1：TP=4、B·T=512、d=4096、bf16。每个 block 两次 all_reduce 的逻辑载荷与 ring 链路量各多少？答：每次 all_reduce 张量 512×4096×2B=4 MB；逻辑载荷每 rank 4 MB（Σ=16 MB）；ring 链路量每 rank 约 2⋅34⋅4=6 MB——公式 2(P−1)/P⋅N 已含算法内部各圈的收发（发送与到达各约 6 MB，两方向合计即此数，不再翻倍）。32 层模型每步 64 次——通信账轻易到百 MB 级，这就是 TP 只在节点内高速互联上做的算术原因。

练习 2：为什么 reduce_scatter + all_gather 可以拼出 all_reduce，且这样拆有意义？答：all_reduce(x) = reduce_scatter(x) 得每 rank 的第 i 块部分和，再 all_gather 拼回完整和——两次操作每 rank 链路量与一次 ring all_reduce 相同，但中间态可以插入计算（如 TP 的 norm 层只需本 rank 的块时，先 reduce_scatter 算 norm 再 all_gather）——把通信切成可重叠的两段，是流水化并行的常用手法（DeepSeek 的 DualPipe 同思想，S17 基础设施节）。

练习 3：PP 两阶段、4 个 microbatch，每阶段耗时 T。流水线气泡占比？答：填满流水线需 1 个 T，排空 1 个 T；总时长 (P+M−1)T=(2+4−1)T=5T，理想 4T（无气泡），气泡 1/5=20%。P 越大或 M 越小气泡占比越高，P−1M+P−1 是公式——增大 microbatch 数（第 9 章的 batch）是直接稀释手段。

练习 4：实验里 [8] 和 [1024] 的 all_reduce 耗时同量级。这说明什么？什么时候字节才开始"值钱"？答：小消息被固定延迟（建链、同步、算法轮次）主导，字节项 bytes/β 可忽略；当 N×4B/β 超过延迟项（在假设 β=10 GB/s 下约 10⁴–10⁵ 元素）后成本才随字节线性。推论：小张量频繁通信是设计坏味道——攒批或融合通信比优化单次更有效；也解释了 10.4 为什么 DP 副本（不传张量）在小模型上吞吐优势明显。

练习 5：8 卡服务一个模型，TP=4×DP=2 与 TP=2×DP=4 各自的通信/显存画像？答：TP=4×2 副本：每卡权重 1/4，每副本内部每 block 2 次 4-way all_reduce（通信重），实例数少、单请求延迟差但能装更大的模型分片；TP=2×4 副本：每卡权重 1/2（模型要装得下一半），通信减半（2-way），吞吐和故障域更好。选型次序：先算显存下限（装得下的最小 TP），再把剩余卡花给副本——通信是税，副本是免税收益。

小结：算了什么、慢在哪里、怎样验证 ​

  • 三种拆法的账：TP 省显存付每层 2×all_reduce，PP 省显存付边界 p2p+气泡，DP 副本免张量通信换吞吐线性——选型先算显存下限再按 SLO 分卡；
  • 原语的账：五个原语的数据流/结果/字节数手算与进程验证一致（0 误差、42 组字节账闭合）；逻辑载荷与 ring 链路量两个口径分开报；
  • 慢在哪里：小消息被固定延迟主导（实测 [8]≈[1024]），大消息进带宽区，batch 摊薄每 token 通信——通信暴露时间 = 字节/带宽 + 延迟，能否重叠看实现；
  • 验证改动的方法：分布式结果 vs 单进程参考 allclose（并行版的"逐 token 一致"）、字节账双算（ByteLog vs 手算）、报错路径显式。
